# 概念缺口：接口抽象与生态约定（协议 / 工厂 / 适配器 / OpenAI 兼容协议）

T6 完成后，用户没有停在"代码能跑"，而是主动追问 `llm.py` 里的三个工程词——协议、工厂函数、适配器；紧接着又追问"OpenAI 兼容协议到底是什么、怎么用"。

这说明用户已经积累了"**能读懂结构**"的直觉，但缺少把这些结构**命名并归因**的词汇。而"协议"这个词在中文里同时指代两件不同的事，是本次最典型的混淆点。

## 暴露的缺口

- **抽象的动机**：知道 `LLMProvider` / `get_llm` 长这样，但说不清"为什么非要这么写"。
- **同名不同义**：`typing.Protocol`（代码内部的形状约定）与 "OpenAI 兼容协议"（网络接口的约定）被同一个中文词覆盖，容易当成一回事。
- **生态常识**：`base_url` 是"换厂商的唯一开关"这件事，此前没有形成认知；也因此容易把"百炼自有协议"与"OpenAI 兼容协议"混在一起。

## Implications

- 讲工程概念时，必须绑定**当前任务里真实存在的那几行代码**，并回答"**不这么写会怎样**"——对照反例比正面定义更有效。
- 遇到中文同名的技术词，要**主动预警并做对比表**，不要假设学习者能自行区分。
- 概念讲完后给出**可亲手跑的验证**（如"写个假模型，证明不继承也能用"），比再多解释都有效。
- 后续 T7–T14 若再出现新的抽象（如 pipeline 的编排函数、评测脚本的结构），沿用课程 0009 的讲法：真实代码 → 反例 → 图示 → 自测。
