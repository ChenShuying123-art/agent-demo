课程 0001 · RAG 项目实战 · 对应任务 T0

从空文件夹到跑起来：拆解 T0

这一课不教你 Python 语法，教的是顺序——拿到一段规格说明后，先做什么、再做什么、每写完一步怎么验证。T0（项目骨架）小到能一次讲透，又刚好把这套顺序完整走一遍。

先读前置课 如果下面的语法或工程概念看不懂（类型注解、类、@dataclass、.env、日志…），先读 前置课：读懂 T0 的每一行。本课假设你已能读顺代码，只讲"顺序与方法"。
学完你能做到：拿到 spec 的一个小节，不靠抄，独立把模块骨架写出来并跑通验收；并且能说清每一步为什么这么排。

一、你不是"不会写"，是"不知道顺序"

照抄能跑、从零就卡——这个差距几乎所有人都会遇到。原因不在语法，而在于：抄的时候答案是现成的；从零写的时候，你要同时决定四件事——

  • 一共要有哪些文件？
  • 每个文件里放什么？
  • 先写哪一个？
  • 怎么知道这一个写对了？

四件事挤在一起，大脑就死机了。新手的本能是"先把整个项目想清楚再动手"，结果永远停在第一步。

破解方法很反直觉：不要试图一次想清楚，而是固定一个顺序，让每一步只回答一个问题。顺序本身就是方法。

二、四步法（这一课真正要带走的）

  1. 先把规格变成清单，一个字代码都不写。
    T0 的 spec 给了字段名、类型、默认值（§7.1）和数据类（§7.2）。你要做的只是把它抄成一张表。这一步看起来"没技术含量"，却决定了后面 80% 的返工——因为返工几乎都来自"没读全就开写"。
  2. 画出依赖箭头，从"没人依赖它"的文件开始写。
    判断标准只有一个：这个文件 import 了谁？谁都不 import 的，最先写。（T0 的顺序：models → config → logging_conf → __init__）
    为什么？因为这样每个文件写完都能立刻单独验证，不会被"还没写完的代码"拖住。反过来从入口 __init__.py 开写，你会立刻陷入"它要调用还不存在的东西"的死循环。
  3. 一次只写一个文件，写完立刻用一行命令验证。
    反馈环越紧越好。写完 config.py 马上跑一句 python -c "..." 看输出对不对。出错时你只改了一个文件，排查范围极小。写完四个文件再一起测，一旦报错，你根本不知道是哪一步的锅。
  4. 最后才把整体连起来跑最终验收。
    跑 python -c "import kbqa"。这时如果失败，问题几乎一定出在"集成"这一层（比如 __init__.py 里的顺序写反了），而不是某一行逻辑——排查方向是明确的。
记住这一句 从叶子往根写，而不是从入口往叶子写。这是新手到"能自己动手"最省力的一次跨越。

三、T0 实战：每个文件"为什么"这么写

先看全貌——四个文件、各自职责、以及它依赖谁（依赖谁决定了书写顺序）：

写的顺序文件它负责什么它依赖谁
1models.py定义数据结构（Document / Chunk…）无
2config.py把 .env 读成一个配置对象pydantic-settings
3logging_conf.py统一日志的格式与级别config
4__init__.py把日志初始化一次logging_conf

1. models.py：为什么它必须是第一个

打开它你会看到，顶部只有三行 import：dataclass、datetime、pathlib——全是标准库，没有一行 import 本项目其他文件。这就是"最底层"的定义。

再看为什么用 @dataclass：它只是给"一坨字段"起个名字，Python 会自动帮你生成 __init__。用它的理由是不需要行为——这些对象只用来装数据。如果它带业务逻辑，就该换成普通类；如果它只是几个字段，dataclass 是性价比最高的选择。

@dataclass
class SearchResult:
    chunk: Chunk
    score: float   # cosine similarity, [-1, 1]
    rank: int

2. config.py：三个"为什么"

这是 T0 里最值得琢磨的文件。

① 为什么 dashscope_api_key: str 后面什么都不给？
其他字段都写了默认值（如 chat_model: str = "qwen-plus"），偏偏密钥没有。这是故意的：没有默认值 = 缺它就直接报错。这叫 fail fast（尽早失败）——宁可启动时立刻崩，也不要带着一个空的密钥继续跑，然后在某个深夜以一个莫名其妙的 401 收场。这背后是工程原则"配置外置"：配置不该写死在代码里，密钥更不该进版本库（见 12-Factor App · 配置（中文））。

② 为什么字段名是小写，而 .env 里是大写？
pydantic-settings 默认大小写不敏感，所以 .env 的 CHAT_MODEL 会自动填到 chat_model。你不必手写转换。

③ 为什么最后要写一句 settings = Settings()？
这是模块级单例：整个项目共用一份配置。如果每个模块各自 Settings()，就会出现"这里读到的模型名和那里不一样"的诡异 bug。一个项目一份配置，是惯例（见 FastAPI 的写法（中文））。

3. logging_conf.py：为什么集中配一次

如果每个文件自己配日志格式，你会看到同一份日志有五种长相。所以规则是：格式只在一个地方定义，各模块只用 logging.getLogger(__name__) 取自己的 logger。这也是项目规范 §18.2 的要求。

4. __init__.py：为什么只有一行

放一句话——初始化日志。为什么放这？因为只要有人 import kbqa，这行就自动执行，日志就统一好了。但如果它顺手 import 了一堆业务模块，那么每 import 一次包，就会连带加载可能很重的东西。包入口越轻越好。

四、亲手做一遍（重点）

看懂 ≠ 会写。下面三个练习都要你真的动手，做完再往下看。

练习 A · 先猜后验 先不要看 kbqa/config.py。打开 docs/spec.md §7.1，把 Settings 的字段名、类型、默认值抄成一张三列表。抄完再对照真实文件，数一数漏了几个、错了几个。
目的：体会"规格 → 清单"这一步有多机械、又有多容易漏。
练习 B · 破坏它，理解 fail fast 把 config.py 里这一行临时改成带默认值的形式：
dashscope_api_key: str = "sk-please-set-me"
然后在没有 .env、也没有环境变量的情况下去 import，观察它是否不再报错。想一想：这种"能跑起来但配置是错的"状态，会在项目的哪个环节给你埋雷？想清楚后把改动还原。
练习 C · 亲手跑一次反馈环 在项目根目录逐个执行（PowerShell）： 
python -c "import kbqa; print('ok')"
python -c "from kbqa.config import settings; print(settings.chat_model, settings.embedding_dim)"
python -c "import logging, kbqa; logging.getLogger('kbqa').info('test')"
第一条对应"models 能加载"，第二条对应"config 读对了"，第三条对应"日志格式对了"。每一条都是一个小到不能再小的验收——这就是第 3 步说的紧反馈环。
提示：没有 .env 时，可临时用 $env:DASHSCOPE_API_KEY='sk-test' 让配置能加载。
