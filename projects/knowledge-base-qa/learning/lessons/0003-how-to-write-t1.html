从函数签名到能跑的代码：拆解 T1

T0 教的是"模块之间的顺序"；这一课往下钻一层，教"单个函数怎么想"。T1 就三个函数，却藏着三个新手必踩的坑，和一个最值得带走的模式——内容寻址。

学完你能做到：拿到 spec 里任意一组函数签名，能独立推出"先写什么、失败怎么办、边界在哪"，并写出能自测通过的实现。
配套：术语表 · 前置 0002 读懂 T0 · 方法 0001 顺序

一、三个新手一定会漏的坑

T1 的三个坑都很小、但都很真实。先记住，再看代码。

坑 1：外部输入不可信（安全）

上传的文件名是用户给的。如果用户把文件名起成 ../../.env，而你直接用它拼路径去写文件，就会覆盖到项目里的其他文件——这叫路径穿越（path traversal）。所以第一步永远是把它"拍平"成一个纯文件名：

safe_name = Path(filename).name   # 只保留最后一段，丢掉任何 ../ 目录

这是"信任边界"的第一课：凡是来自程序外部的东西（用户输入、网络请求），都当作不可信。

坑 2：编码必须显式写

读文件时如果不指定编码，Python 会用系统默认——在 Windows 上不是 UTF-8，于是中文文档一读就乱码、甚至直接抛 UnicodeDecodeError。

path.read_text(encoding="utf-8")   # 不写 encoding，换台电脑就可能崩

坑 3：磁盘才是真相

文件大小、上传时间，别"记"在上传参数里，要去问磁盘：

stat = path.stat()          # 现读现取
size = stat.st_size         # 而不是信 len(content) 或客户端报的值

为什么？因为文件可能被改过、被换过。以磁盘为准，数据永远不会自相矛盾。

二、怎么从 spec 写出代码：五步

  1. 先把三个函数签名抄下来。 spec §7.3 给了名字、参数、返回。签名就是图纸——输入→输出想清楚了，实现只是填空。
  2. 每个函数只回答三个问题：给我什么？还我什么？失败会怎样？第三个问题新手最容易漏，但它直接决定你要不要 raise。
  3. 先写最顺的那条路（happy path）。 假装一切正常，把能跑通的最短代码写出来。别一上来就想着所有异常。
  4. 立刻跑一个能看见结果的例子。 别写完三个函数再一起测——这是 T0 就讲过的紧反馈环。
  5. 回头补边界。 目录不存在怎么办？后缀不对怎么办？空列表怎么办？验收清单里的每一条，都是要补的边界。
关键心态 你不是在"写代码"，你是在回答一堆小问题。每个函数拆成 3 个小问题，难题就不见了。

三、逐函数拆解

load_document(path) -> str：最小、但边界最多

逻辑一句话：按后缀判断，然后读文本。值得学的是它把错误说清楚：

suffix = path.suffix.lower()
if suffix not in SUPPORTED_SUFFIXES:
    raise ValueError(f"不支持的文件类型：{path.name}（仅支持 {sorted(SUPPORTED_SUFFIXES)}）")
return path.read_text(encoding="utf-8")

为什么 raise ValueError 而不是默默返回空字符串？因为静默失败比报错更可怕：那会让错误一路飘到很远的地方才炸，且看不出源头。这和 T0 的 fail fast 是同一个思路。

还有个细节：md 文件故意不做任何清洗（不去掉 #）。因为标题层级是后面切分时的"强边界"，提前剥掉就丢信息了。

save_upload(...)：本任务的核心

它要同时做三件事：落盘、去重、返回描述。顺序很重要：

# ① 先消毒文件名（坑 1）
safe_name = Path(filename).name

# ② 用内容算 id —— 内容相同，id 就相同
doc_id = _compute_doc_id(content)      # sha256 前 16 位

# ③ 去重：id 已存在就直接返回，不再落盘
existing = next(iter(uploads_dir.glob(_stored_name(doc_id, "*"))), None)
if existing is not None:
    return _to_document(existing, doc_id, ...)

# ④ 落盘，文件名带上 id 前缀
stored_path = uploads_dir / _stored_name(doc_id, safe_name)

为什么文件名要写成 {doc_id}_{原名}？这个小小的命名约定，一次解决了三个问题：

  • 判重只需一次 glob —— 快
  • 原始文件名还在磁盘名里 —— 不用额外元数据就能还原展示名
  • id 肉眼可见 —— 看日志、看目录都能对上

这是个通用教训：好的命名约定，能让代码少写一半逻辑。

list_documents(data_dir)：过滤 + 还原

扫目录时，不是所有文件都是文档——.gitkeep、或别人手动丢进来的文件都要跳过。所以有一个 _is_upload_file() 专门判断"这个文件名是不是我自己写出来的格式"。判断通过，再从文件名反解出 doc_id 和原名。这一步就是坑 3 的落地：size 和时间都从 stat() 现取。

四、一个值得带走的模式：内容寻址

T1 最值钱的思想就一句话：用内容算出的哈希，当内容的唯一标识。这叫内容寻址（content addressing）。

如果 id 用…会怎样
文件名同内容不同名 → 存两份；改名 → 变成"新文档"
上传时间同一份文件传两次 → 两份，永远去不了重
内容哈希内容一样就是同一个 → 天然去重，还顺带能校验有没有损坏

你其实天天在用这个思想：Git 的 commit、Docker 的镜像层、网盘的"秒传"，全是内容寻址。T1 里的 doc_id = sha256(内容)[:16] 就是它的迷你版。

顺带一提：哈希只取前 16 位（而不是完整 64 位），是"碰撞概率低到可忽略"与"名字要短"之间的工程折中。
