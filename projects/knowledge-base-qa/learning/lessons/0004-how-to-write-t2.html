一、T2 的真正难点：把模糊的词变成精确的规则

spec §7.4 的策略是自然语言写的，第一条就是："先按空行切分段落；md 的 # 标题行作为强边界。"

这句话不能直接写成代码——你必须先回答四个问题：

模糊的说法必须变成的精确规则
"空行"正则 \n[ \t]*\n（两个换行之间只有空白）
"边界"一个位置（段落的起点），不是一段文字
"# 标题行"行首 ≤3 空格 + 1~6 个 # + 一个空白字符
"强"边界"优先选它"，即搜索时先搜强边界，搜不到再退而求其次

这一步就是全部功夫。 新手写不出来，往往不是不会写循环，而是没有把"空行""强边界"这些词逼问成可判定的事实。

二、核心套路：先枚举候选，再做选择

一个常见的错误思路是"一边扫描一边切"——那样要同时维护一堆状态，很容易乱。更好的做法分两步：

  1. 先把"所有允许切的位置"算出来，分成强边界（标题/段落）和弱边界（换行/句末）两级。这一步只产出位置，不产出文本。
  2. 再逐块贪心选择：在窗口 (start + overlap, start + chunk_size] 里，挑最大的那个候选切点。

主干只有这么几行：

start = 0
while True:
    limit = start + chunk_size
    if limit >= n:
        end = n                       # 剩下不足一块，直接收尾
    else:
        end = 最大候选切点 in (start + overlap, limit]   # 强边界优先，其次弱边界
        if end is None:
            end = limit               # 附近没有边界：硬切
    产出 chunk(start, end)
    if end >= n:
        break
    start = end - chunk_overlap       # 回退，形成重叠

"先枚举候选、再做选择"是个很通用的拆解思路：把"在哪里做决定"和"怎么做决定"分开，各自都很简单。

三、五个必须想清楚的点

1. 位置不变量：text[start:end] == chunk_text

这是 T2 验收里单独列出的第 ③ 条，也是最重要的一条。为什么？ 因为后面做问答时要给出引用——"这句话出自原文第几段"。如果 start/end 错位一个字符，引用就会指到别处。

这类"任何情况下都必须成立"的断言叫不变量（invariant）。写算法时先问自己"什么必须永远成立"，再把它写成断言去跑——这比事后肉眼检查可靠得多。

2. 重叠怎么做到"恰好"是 overlap

很多人会想"把上一块的尾巴拼到下一块的头上"。其实不用拼接，只要一个减法：

start = end - chunk_overlap   # 下一块的起点 = 上一块的终点 - overlap

这样相邻两块的重叠恰好是 chunk_overlap 个字符，不需要任何额外的拼接或裁剪。

3. 这个循环一定会前进吗？（防死循环）

写 while 时最该问的一句话是：每轮结束，位置一定往前走吗？

如果 overlap >= chunk_size，那么每块最多推进 0 个字符——位置原地踏步，程序永远跑不完。所以开头就把 overlap 收窄到 chunk_size - 1，并打一条 WARNING（让调用者知道配置被改过，而不是默默出错）。

4. 优先级：强边界 > 弱边界 > 硬切

为什么把 md 的 # 标题当强边界？因为标题代表新章节。如果一个 chunk 横跨两个章节，它讲的是两件事——检索命中它时，内容会"驴唇不对马嘴"。为了语义干净，宁可让这个 chunk 短一点。

5. 窗口下界为什么用 start + overlap

如果允许在紧挨着起点的位置切（比如只前进 3 个字符），下一块就几乎和上一块一模一样，既浪费又危险。要求"本块必须比 overlap 长"，一举两得：既保证重叠完整，又保证一定能前进。

一句话总结 算法的正确性，往往不取决于主流程，而取决于这几条边界规则。写之前先把边界想清楚，代码会短得让你意外。

四、实测数据：chunk_size 到底怎么选

拿 docs/spec.md（32655 字符）实跑，overlap 固定 80：

chunk_sizechunk 数平均每块
200370约 88 字符（扣除重叠）
50096约 340 字符
80056约 580 字符

规律：size 越小，chunk 数近似线性增长。这带来一个权衡——

  • 太小 → 每块信息不全，检索到的片段"缺胳膊少腿"，模型答不完整；
  • 太大 → 每块混入很多无关内容，噪声拉低答案质量，还浪费上下文长度。

500 是个常见起点，不是标准答案。§13 的评测会告诉你，对你自己的文档来说哪个更好。
