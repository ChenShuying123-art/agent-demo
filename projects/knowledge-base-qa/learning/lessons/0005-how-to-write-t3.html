把代码接上真实世界：拆解 T3

前四课都在你本机跑。这一课是第一次把代码接到外部服务——于是多出三样东西：配额、凭据、失败。T3 的代码不长，但真实的坑这次真的踩到了，值得记一辈子。

学完你能做到：调用任何"有单次条数上限"的外部接口时，能正确分批、并证明顺序没错；也终于弄清 .env 和 .env.example 的区别。
配套：术语表 · 前置 0003 / 0004

一、接上外部服务，多出哪三件事

新增的东西对代码的影响
配额/上限接口不是无限收的。这次是"单次最多 10 条"——于是必须分批。
凭据要带上 API Key，于是有了"密钥该放哪"的问题（这一课的重点之一）。
失败网络会抖、额度会用完。于是要有重试，且失败时要能看出原因。

这也是为什么 T3 之前可以先"离线"做的都做了——把能本地验证的先钉死，接外部服务时才只需面对真正的新问题。

二、分批：不是优化，是硬限制

官方文档写得很明确：text-embedding-v4 的"最大行数"是 10（见 阿里云百炼官方文档）。所以这不是"分批更快"，而是不分批就直接报错。

代码里对应的是最简单的那种写法——按顺序切、同步发、顺序拼回去：

for batch_no, start in enumerate(range(0, len(texts), self._batch_size), start=1):
    batch = texts[start : start + self._batch_size]
    vectors.extend(self._embed_one_batch(batch_no, batch))   # 按批顺序拼回

顺带一提：代码里还有一道"防呆"——如果配置把 batch_size 调到 20，会强制拉回 10 并打 WARNING。宁可配置被纠正，也不要等到调用时才炸。

三、顺序：最隐蔽的坑（错了不报错）

想想看，如果分批后顺序乱了会怎样？

不会报错。 程序照常返回 15 个向量，长度也对。但第 3 个向量其实是第 7 条文本的——于是"这条 chunk 对应哪个向量"全错位，检索出来的结果整体偏移，而且你看不出问题在哪。

这就是为什么 T3 的验收把这个单独列一条。一个 bug 最可怕的地方不是它存在，而是它沉默。

怎么证明顺序没错？——逆序验证法

把同一批文本整体倒过来再跑一遍：如果顺序逻辑是对的，结果应该正好是原来的逆序。用余弦相似度逐位比较：

v1 = embedder.embed(texts)
v2 = embedder.embed(list(reversed(texts)))
worst = min(cos(v2[i], v1[len(v1) - 1 - i]) for i in range(len(v1)))
# ≈ 1 才说明顺序没乱

实测结果：最差余弦 = 1.000000。这个"变换输入、预测输出"的验证思路，比"肉眼看结果对不对"强得多。

四、实测观测数据

用真实接口跑出来的数字（对应 spec §10 索引第 3 步的观测点）：

观测点实测值说明
分批次数15 条 → 2 批（10 + 5）验证了"内部自动分批"
向量维度1024与 embedding_dim 一致
L2 范数1.0000接口本身就返回单位向量
前 5 维[-0.014346, -0.01275, 0.038668, -0.007353, 0.033195]数值很小、有正有负，正常
语义相近 / 无关0.9301 / 0.8952相近确实更高，但差距不大
两个值得记住的观察 ① L2 范数正好是 1.0 —— 说明接口已经帮你归一化了。所以 T4 里"再归一化一次"是个安全的空操作，不是多余步骤（换个模型就可能需要）。
② 语义相近 0.93、完全无关也有 0.90 —— 差距很小。说明这类模型的分数尺度整体偏高。所以判断"有多相关"要看排序，不要看绝对值（spec §11 也提到这一点）。这个特性到 T8 重排时会更明显地感受到。

五、真实踩到的坑：Key 填进了 .env.example

这一条是这次做 T3 时真的发生的，不是编的。

现象：你说"Key 已经配好了"，但程序读不到。原因是 —— Key 被填进了 .env.example。而这个文件是 git 跟踪的模板，结果它跟着一次提交进入了 git 历史。所幸那次提交还没有 push，才没有真的泄露到远程。

文件角色能不能提交
.env.example模板，只有占位符 sk-xxxxxxxx要提交（告诉别人需要哪些配置）
.env你的真实配置（含 Key）绝不提交（已在 .gitignore 里）

正确流程永远是这两步：

  1. copy .env.example .env（复制出真配置）
  2. 把真实 Key 只填进 .env；.env.example 保持占位符不动
如果不小心把 Key 提交了怎么办 按严重度排序处理：① 立刻去控制台作废并重新生成 Key（这一步最重要，换钥匙比擦痕迹简单得多）；② 把 Key 从工作区挪进 .env，还原 .env.example；③ 若那次提交还没 push，用 git commit --amend 把它改写掉；已经 push 了则视为"已泄露"，只能靠换 Key 解决。

还有一个细节：.env 能生效的前提是你的工作目录就是项目根目录——配置是"相对当前目录"去找 .env 的。所以别在别的目录里跑脚本，否则会读不到。
