课程 0006 · RAG 项目实战 · 对应任务 T4

让数据永不"错位"：拆解 T4

T4 表面上是"把向量存起来"，真正的难点却是三份文件必须永远对齐——一旦错位，检索会拿到"别人的向量 + 这段文字"，而且不报错。这一课讲的就是：怎么让这种错误不可能发生，以及发生了怎么立刻发现。

学完你能做到：设计任何"多份数据要保持同步"的存储时，能说清谁是"真相源"、怎么用一次操作同时更新两边、以及把自己最怕的错误写成一条断言。
配套：术语表 · 前置 0004 / 0005

一、T4 的坑：三份数据，一条命

索引落在三个文件里：

文件内容
vectors.npy第 i 行 = 第 i 个 chunk 的向量
chunks.jsonl第 i 行 = 第 i 个 chunk 的原文
docs.json每篇文档索引了多少 chunk

关键约束：第 i 行向量必须和第 i 行文字属于同一个 chunk。这叫做"行序同步"。

如果哪天两者差了 1 行——比如删文档时只删了文字、忘了删向量——后果是什么？向量还在、文字少了一段，于是整条索引从删除点之后全体错位。检索命中的是"A 文档的向量"，拿出来的却是"B 文档的文字"，而程序一声不吭。

这类 bug 的可怕之处和 T3 的顺序问题一模一样：它不报错。所以对付它不能靠"小心"，要靠机制。

二、机制一：用同一个操作，同时更新两边

看删除是怎么写的：

keep = [i for i, chunk in enumerate(self._chunks) if chunk.doc_id != doc_id]
self._chunks  = [self._chunks[i] for i in keep]
self._vectors = self._vectors[keep]

它不是"先删文字、再删向量"，而是"先算出保留哪些行，再让两边用同一份 keep 各自重建"。这样两边天然同步，根本不存在"只删了一边"的中间状态。

这是个很值得记住的思路：不要写"两步操作"，写"一次计算 + 两边应用"。 要求"两个操作都成功"的地方，最好设计成"只需要一个操作"。

三、机制二：把最怕的错误写成断言

def _assert_rows_aligned(self) -> None:
    if self._vectors.shape[0] != len(self._chunks):
        logger.error("npy 行数(%d) != jsonl 行数(%d)，行序已失步", ...)
        raise AssertionError("向量行数与 chunk 数不一致，索引行序失步")

这个方法在 add / remove / load 之后都会调用。它做的事只有一件：核对那条"必须永远成立"的约束。

这正是 T2 学过的不变量的又一次应用：先想清楚"什么必须永远为真"，把它写成可执行的检查，而不是靠肉眼。

一句话方法论 写存储代码时先问自己："我最怕哪个数字对不上？" 然后为它写一条断言。
这里最怕的就是：vectors.npy 的行数 ≠ chunks.jsonl 的行数。

四、三个"为什么"

① 为什么存之前要 L2 归一化？

归一化后每个向量的长度都是 1，此时"点积"恰好等于"余弦相似度"。于是整库相似度可以写成一次矩阵乘法：

scores = self._vectors @ query      # 一次算完 N 条，不用逐条算余弦

T3 已经发现：百炼接口本来就返回单位向量（L2 范数 = 1.0）。所以这一步在这里是"安全的空操作"——但换个模型可能就不是了，留着它才稳。

② 为什么用 argpartition 而不是直接排序？

因为我们要的只是"前 k 个"，不是"完整的顺序"。

  • 全排序：O(N log N)，把 10000 条全部排好，但你只用前 4 条
  • argpartition：O(N)，只保证"前 k 个是最大的"

代价是：argpartition 不保证这 k 个内部有序，所以要再对选中的 k 个排一次（k 很小，几乎不要钱）。"先粗挑、再精排"——这个套路在后面 Rerank 里还会遇到一次，只不过那次是语义层面的。

③ 为什么删除要立刻落盘，而新增不用？

操作是否立刻写文件理由
remove_document是删除必须马上生效，否则崩溃后"删掉的向量"会从文件里复活
add否（交给 save()）新增是批量行为，反复重写大文件很浪费

"什么时候必须立刻持久化"是个真实的工程判断，没有标准答案——但每个选择都要能说出理由。

五、顺带学一个工程习惯：幂等

Notebook 里入库那一步我写成了这样：

store.remove_document(doc.doc_id)   # 重新索引 = 先删后加
store.add(chunk_objs, vectors)

为什么先删？因为直接 add 会累积重复：Notebook 跑第二遍，同一批 chunk 就进库两次，检索结果里全是重复片段。

"先删后加"让这一步变成幂等的——执行一次和执行三次，结果一样。写脚本、写 Notebook、写定时任务时，尽量让每一步都能安全地重复运行，你会少掉很多"跑第二遍就坏了"的麻烦。
