课程 0007 · RAG 项目实战 · 对应任务 T5

结果不可思议时，先怀疑工具

T5 的代码本身很短。真正耗掉时间的，是"为什么结果不对"。这一课的重点不是 Rerank 本身，而是一套排查问题的套路——以及一个 Windows 上真实存在、会让你怀疑人生的编码陷阱。

学完你能做到：当结果"不可思议"时，不再靠猜和换方案，而是用"对照实验 + 让工具自证"两步定位到真凶。
配套：术语表 · 前置 0004 / 0006

一、T5 在做什么

检索分两个阶段：召回（快、粗，取 20 条）→ 重排（慢、准，取 4 条）。

为什么召回之后还要重排？因为召回用的是 Bi-encoder（双塔）：查询和文档各自独立编码成向量，可以离线预计算、快，但两者之间没有交互，精度有限。重排用的是 Cross-encoder（交叉编码器）：把"查询 + 文档"拼在一起过模型，能捕捉细粒度交互，准得多——代价是没法预计算，只能对少量候选做。

这就是"两阶段检索"的分工：用便宜的方法保证不漏，用昂贵的方法保证排序。

二、三个必须做对的地方

要点为什么
响应的 index 必须用来映射回原候选它只是"输入数组的下标"。不回映射就拿不到 chunk 的 doc_id / 文件名 / 原文位置
relevance_score 与 cosine 尺度不同两者不可比较，所以单独存字段，绝不混着排序
必须记录 original_rank这是本项目最有价值的可观测数据——能一眼看出"谁被顶上来了"

降级：为什么不能抛异常

重排失败时，代码选择退化成"直接取召回前 N 条"，并给每条打上 degraded=True，而不是把异常往上抛。

理由是：重排只是"锦上添花"，不是问答链路的必需品。为了它让整个问答挂掉，不划算。但降级必须被标记出来——否则用户看到的是"排过序的结果"，实际上根本没排，这是另一种形式的"静默错误"。

三、⚠️ 真实的排查过程（本课重点）

下面这些是真实发生的，不是编的。

症状

问"召回和重排有什么区别？"，4 条候选里只有 1 条相关。结果却是：

[(2, 0.6674), (3, 0.6674), (1, 0.6357), (0, 0.6068)]
                ↑ 两条无关项分数一模一样          ↑ 相关的那条排最后

错误的第一反应

我判断"模型大概没开通"，让你去控制台确认——结果控制台显示已开通，额度也在正常扣。这个方向被证伪了。

四个正确动作，逐个逼近真相

  1. 先确认结果可复现。 同一请求跑两遍，结果一模一样 → 不是随机抖动，是稳定行为。
  2. 让工具自证：请求 return_documents=true。 让接口把每条文档的原文一起回显。结果回显的 index 与原文完全对得上 → 排除"下标映射错位"。
  3. 做一个"结论必然如此"的对照实验。 把同一组内容翻译成英文再跑一遍：英文结果是 [(0, 0.9189), (3, 0.2046), ...]——完美。同一个模型、同一套代码，英文对、中文错 → 问题一定出在语言 / 编码这条线上。
  4. 换一条传输路径。 之前我一直用终端管道把脚本喂给 python -。这次把脚本写成真正的 .py 文件（UTF-8）再运行——中文也完美了：[(0, 0.931), (3, 0.2092), ...]。
真凶 PowerShell 把含中文的脚本文本通过管道传给 python - 时，中文被按控制台代码页编码，真的损坏了——不只是显示成 ?，而是发到模型那边就是乱码。模型拿到乱码，自然给出一堆"挤在一起、排序错乱"的分数。

英文是 ASCII，任何编码都坏不了，所以英文测试一直是对的——这也正是它能当"对照实验"的原因。

一条硬规则

凡含中文（任何非 ASCII 字符）的验证脚本，一律写成 .py 文件再运行，不要用管道喂 stdin。

这条规则的代价我刚刚付过：因为误判成"模型不可用"，白跑了一轮控制台确认，差点把一个好模型换掉。

四、可复用的排查套路

动作解决什么
跑两遍看是否稳定排除随机性，确认是"稳定行为"而不是偶发
让工具自证（回显 / 打印中间值）排除"数据在传递中变了形"
做"结论必然如此"的对照实验把问题一刀切到某个维度（这里是"中文 vs 英文"）
换一条传输 / 执行路径排除工具链本身引入的失真
缩到最小可复现案例区分"普遍问题"还是"特定条件下的问题"
一句话 结果"不可思议"时，先怀疑你的验证工具，再怀疑被验证的对象。因为"工具错了"的典型特征，就是"结果离谱到不像真的"。
