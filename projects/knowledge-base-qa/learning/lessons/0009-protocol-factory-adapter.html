协议、工厂、适配器，以及"OpenAI 兼容协议"

这一课把四个容易糊在一起的词串起来：协议 / 工厂 / 适配器 / OpenAI 兼容协议。它们背后其实是同一个思想——把"变化"关进一个笼子里。

学完你能做到：看懂三个 Provider 模块（embeddings / rerank / llm）为什么长得一样；知道换模型、换厂商时该改哪里；以及为什么重排不能用 openai SDK。
配套：术语表 · 前置 课程 0008

一、总纲：一句话串起四个词

记住这句 协议定形状 → 适配器把外部实现改造成这个形状 → 工厂决定用哪个。

"OpenAI 兼容协议"则是这套思想在现实世界里的一个现成例子——厂商们共用同一种"形状"。

协议 Protocol「谁有 chat() 这个方法，谁就合格」
↓ 谁符合这个形状？
适配器DashScopeChat
翻译接口与异常
替身（测试用）FakeChat
不联网、不花钱
↓ 谁来创建？
工厂 get_llm()「用哪个实现」只在这里决定
↓
调用方拿到一个 LLMProvider它不知道背后是百炼、还是别的厂商
图 1 · 协议 → 适配器 → 工厂，三者是一条流水线

二、协议 Protocol —— 只规定"能干什么" 语法

先看一个类比的场景

招人时你写的是岗位要求："会写 Python、能搬 20 公斤、有驾照"。你不在乎他哪个学校毕业、什么血型——只要满足这几条，就能上岗。

Protocol 就是这份岗位要求。看 llm.py：

class LLMProvider(Protocol):
    def chat(self, messages: list[dict], temperature: float | None = None) -> str:
        ...

翻译成人话："我不管你是谁，只要你有 chat 这个方法、能收 messages 返回一段文本，你就算 LLMProvider。"

最反直觉的一点

看下面这两行——DashScopeChat 并没有继承 LLMProvider：

class LLMProvider(Protocol): ...   # 只是"要求"
class DashScopeChat:               # 注意括号里是空的！
    def chat(...): ...

这是 Protocol 和普通继承最大的区别：

普通继承 / 抽象基类Protocol
判断依据你声明自己是谁（class A(B)）你长得像不像（有没有那个方法）
换个说法看血统看形状
术语名义类型（nominal）结构类型（structural）

Python 里有句老话叫 duck typing（鸭子类型）："走起来像鸭子、叫起来像鸭子，那它就是鸭子。" Protocol 就是把这句话写进代码、让工具能检查。

它到底给你带来什么

假设调用方写成这样（只依赖"形状"）：

def answer(question: str, llm: LLMProvider):   # 只要形状对
    return llm.chat([{"role": "user", "content": question}])

下面这些全都能直接塞进去，answer 一个字都不用改：

  • DashScopeChat(settings)
  • 换个厂商写的 OtherVendorChat(settings)
  • 测试用的假模型
亲手试一下（很值） 
class 假模型:                       # 不继承任何东西
    def chat(self, messages, temperature=None) -> str:
        return "这是假答案"

def ask(provider, question):
    return provider.chat([{"role": "user", "content": question}])

print(ask(假模型(), "你好"))       # 输出：这是假答案
完全不需要真实 API、不花钱、不联网。 这就是为什么"面向协议编程"能让测试变简单——你可以把慢的、贵的、不稳定的外部依赖，换成一个形状一致的替身。
必须坦白的一点 Protocol 在运行时几乎不做检查。你方法名拼错了，Python 照样让你跑到那一行才报 AttributeError。所以它真正的用途是：① 给读代码的人看（一眼知道该有哪些方法）；② 给类型检查器（mypy）看（写代码时就报错）。@runtime_checkable 是可选增强，让 isinstance() 也能用，但它只查"方法在不在"，查不了参数类型。

三、工厂函数 —— 只在一个地方决定"用哪个" 工程

去餐厅点"一杯咖啡"，你不需要知道用的是哪台咖啡机、哪批豆子。你对着菜单说一句，后厨负责决定。

def get_llm(settings: Settings) -> LLMProvider:
    return DashScopeChat(settings)

没有工厂会怎样

假设 3 个地方要用模型，各写一遍：

# pipeline.py
self._llm = DashScopeChat(settings)
# evaluate.py
llm = DashScopeChat(settings)
# api/routes.py
llm = DashScopeChat(settings)

现在要换厂商——得改 3 处。只要漏一处，就会出现"索引用 A 模型、问答用 B 模型"这种极难排查的诡异 bug。有了工厂：改 1 处。

注意返回类型 -> LLMProvider

这是工厂和协议之间的扣：工厂返回的是协议类型（形状），不是 DashScopeChat（具体类）。所以调用方拿到的永远是"一个能满足 LLMProvider 的东西"，它压根不知道、也不该知道背后是谁。

项目里还有个更妙的例子

工厂还能替你做决策。看 rerank.py：

def get_reranker(settings: Settings) -> RerankProvider | None:
    if not settings.rerank_enabled:
        return None            # ← 连"要不要有这个对象"都帮你决定了
    return DashScopeReranker(settings)

调用方只需要 if reranker is None: 跳过重排。"要不要开重排"这个判断只写了一遍，而不是散落在每个调用点。

四、适配器 —— 在边界上"翻译" 工程

出国旅行插座形状不一样，你带个转换插头：你的电器不用改，国外的电网也不用改——转换头承担了全部差异。

在 llm.py 里，这个转换头翻译了两样东西。

翻译一：接口形状

外面的 SDK 长这样（model / messages / extra_body 都是 SDK 的习惯）：

self._client.chat.completions.create(
    model=..., messages=..., temperature=..., extra_body=...
)

你的项目只认一个简单形状：llm.chat(messages)。差异被 DashScopeChat 吃掉了。

翻译二：异常形状（这个更重要）

外面抛的异常五花八门，长这样：

openai.AuthenticationError(
    body={"error": {"code": "invalid_api_key", "message": "..."}}
)

你的项目只想要一个稳定的形状，所以在边界上翻译一次：

except Exception as exc:
    code = _error_code(exc)                                  # 从外部形状里挖出 code
    raise LLMError(f"LLM 调用失败 code={code}：{exc}", code) from exc
不翻译翻译之后
上层要写except openai.AuthenticationError
except openai.RateLimitError
except openai.APIConnectionError
…每处调用都要重复		except LLMError as e
读 e.code 即可
换厂商时上层的 except 全都要改上层不用动

注意最后那行 from exc——这叫异常链，它保留原始异常的堆栈。翻译不能翻译掉线索。而 _error_code() 就是那本"翻译词典"：它知道外面可能有几种写法，挨个试，最后兜底用 HTTP 状态码。

五、⚠️ 注意：此"协议"非彼"协议"

你刚学的 typing.Protocol 和接下来要讲的"OpenAI 兼容协议"，是两个完全不同的东西，只是中文都译成了"协议"：

typing.Protocol"OpenAI 兼容协议"
层面Python 代码内部的约定网络接口上的约定
约定什么有哪些方法、什么签名URL 路径、请求字段、响应结构
谁看类型检查器 + 读代码的人客户端 SDK + 服务端
类比"岗位要求""插座标准"
但精神是同一个 先约定好形状，双方各自实现，就能互相对接。理解了这一点，你就抓住了这两个词的本质。

六、OpenAI 兼容协议 —— 它是什么

OpenAI 的 chat/completions 接口太流行了，成了事实标准。

于是其他厂商（阿里云百炼、DeepSeek、月之暗面、智谱……）做了一件很聪明的事：把自己的接口做成"形状和 OpenAI 一模一样"。好处是——你现有的 OpenAI 代码，改两行就能跑在百炼上。

它不是国际标准组织发布的标准，没有 RFC 文档。它是"因为大家都这么干，所以成了约定"——工程界叫事实标准（de facto standard）。

它具体"兼容"了四样东西

兼容项OpenAI 的写法百炼照抄的
URL 路径/v1/chat/completions/compatible-mode/v1/chat/completions
请求体字段model / messages / temperature完全一样
响应结构resp.choices[0].message.content完全一样
错误格式{"error": {"code", "message"}}基本一样

注意路径里那个 compatible-mode（兼容模式）就是在自报家门："我这里是照着 OpenAI 的样子做的。"

七、怎么用：真的只改两处

from openai import OpenAI

client = OpenAI(
    api_key="sk-xxx",                                              # ← 改这里
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",  # ← 改这里
)

resp = client.chat.completions.create(
    model="qwen-plus",                     # ← 和这里（换成百炼的模型名）
    messages=[{"role": "user", "content": "你好"}],
)

print(resp.choices[0].message.content)

就这些。你写的是"OpenAI 的代码"，实际请求打到的是阿里云。本项目 llm.py 就是这么干的：

self._client = OpenAI(
    api_key=settings.dashscope_api_key,
    base_url=settings.chat_base_url,     # = .../compatible-mode/v1
)
一句话 真正的魔法不在代码里，在 base_url 那一个字符串上。

八、项目里的活证据

回到 config.py，三个 URL 形成了鲜明对比：

# 对话 —— 走 OpenAI 兼容
chat_base_url      = "https://dashscope.aliyuncs.com/compatible-mode/v1"

# Embedding —— 也走 OpenAI 兼容（注意：和上面是同一个 URL！）
embedding_base_url = "https://dashscope.aliyuncs.com/compatible-mode/v1"

# Rerank —— 不走兼容，是百炼自有协议
rerank_endpoint    = "https://dashscope.aliyuncs.com/api/v1/services/rerank/text-rerank/text-rerank"

观察一：对话和向量用的是同一个 base_url

那服务端怎么知道你要聊天还是算向量？靠 model 名区分。

client.chat.completions.create(model="qwen-plus", ...)          # 聊天
client.embeddings.create(model="text-embedding-v4", ...)        # 向量

观察二：Rerank 的 URL 长得完全不一样

它没有 compatible-mode。这就是为什么 rerank.py 里没有用 openai SDK，而是用 httpx 手写 HTTP 请求——它压根不走 OpenAI 兼容协议。

对话 / 向量compatible-mode/v1
OpenAI 兼容 → 用 openai SDK
重排（Rerank）api/v1/services/rerank/…
自有协议 → 只能用 httpx 手写
图 2 · 同一个平台，两套协议；走不走"兼容"决定了你用什么工具

这也顺便解释了你之前看到的那个坑：重排的请求体是 {input: {query, documents}, parameters: {top_n}}，和 OpenAI 的扁平风格完全不同——因为它根本不是 OpenAI 的形状。

九、⚠️ "兼容"不等于"完全一样"

兼容是"大部分一样"，不是"全部一样"。差异主要有三类：

差异类型例子怎么处理
厂商私有参数enable_thinking（百炼独有）塞进 extra_body={...}
额外的响应字段reasoning_content（思考过程）用 getattr 取
能力支持不完全某些 tools / response_format 行为不同得实测确认

这正好解释了你代码里那行 extra_body：

resp = self._client.chat.completions.create(
    model=self._model,
    messages=messages,
    temperature=temp,                                        # ← 标准字段，直接传
    extra_body={"enable_thinking": self._enable_thinking},   # ← 私有字段，只能走 extra_body
)

为什么 enable_thinking 非得包一层？因为 OpenAI SDK 不认识它——SDK 是按 OpenAI 的规格写的，遇到不认识的参数会直接报错。extra_body 就是官方留的"协议之外，我自己加点东西"的逃生口。

一句话 extra_body 里的东西，就是"兼容协议"没覆盖到的地方。

因为这套东西不止百炼一家在学。你学会之后：

平台base_url要改的地方

十一、纵深：把三套适配器放在一起看 工程

前面几节都以 llm.py 举例。其实项目里有三套完全对称的结构——凡是要连"外部世界"的地方，都是同一个套路：

角色对话向量重排
协议LLMProvider（chat）EmbeddingProvider（embed / dim）RerankProvider（rerank）
适配器DashScopeChatDashScopeEmbeddingDashScopeRerank
工厂get_llm()get_embedding_provider()get_reranker()
调用方RAGPipeline / api——只认协议

三个文件里，"协议在最上、适配器在中间、工厂在最后"的顺序一模一样。这不是巧合，是刻意统一——看懂一个，另外两个不用看。

证据：调用方根本不认识"外部世界"

这是整节最关键的一点。看 kbqa/pipeline.py 的全部 import：

from kbqa.embeddings import EmbeddingProvider    # ← 只 import 协议
from kbqa.llm import LLMProvider
from kbqa.rerank import RerankProvider
# 注意：整个文件里没有 openai，也没有 httpx

构造函数里的类型注解同样只写协议：

def __init__(self, settings, store,
             embedder: EmbeddingProvider,       # 不是 DashScopeEmbedding
             reranker: RerankProvider | None,
             llm: LLMProvider): ...
可以自己去验 在项目根目录跑：grep -n "openai\|httpx" kbqa/pipeline.py —— 没有任何输出。 也就是说：编排层从头到尾不知道百炼、不知道 http、不知道 SDK 的存在。

适配器到底"翻译"了几样东西（本项目真实清单）

#消化了什么在哪例子
1接口形状DashScopeChat / DashScopeRerankchat.completions.create(...) vs httpx.post(endpoint, json={...})——两套完全不同的协议，对外都是"给输入，还结果"
2厂商私有参数DashScopeChatextra_body={"enable_thinking": False}
3返回值归一DashScopeRerank响应的 index → 映射回 chunk；relevance_score → rerank_score
4异常形状DashScopeChat各种 SDK 异常 → 带 code 的 LLMError
5吸收不可靠性DashScopeRerank调用失败 → 返回 degraded=True 的降级结果，不抛异常

第 5 条最容易被忽略，也最重要：

except Exception as exc:                      # 网络/协议/鉴权任何问题
    logger.warning("rerank 调用失败，已降级为直接截断前 %d 条：%s", top_n, exc)
    return self._fallback(candidates, top_n)  # ← 不让整条问答链路跟着崩

外部服务会挂、会超时、会返回怪东西——这些"脏活"全在适配器里消化掉，上层永远拿到形状稳定、含义明确的结果（哪怕是明确标记过的降级结果）。

"换实现只改一处"——到底改哪一处

你想做的事要改的地方完全不用碰
换对话模型（qwen-plus → qwen-max）.env 一行 CHAT_MODEL=所有代码
关掉重排做消融实验.env 的 RERANK_ENABLED=false代码（工厂返回 None，pipeline 已处理）
换厂商 / 接自建兼容服务新写一个适配器 + get_llm 改一行pipeline / api / 前端
测试时不花一分钱写个 FakeLLM + 让工厂按开关返回它同上

装配点也只有一个地方（api/main.py）：

pipeline = RAGPipeline(settings=settings, store=store,
    embedder=get_embedding_provider(settings),   # 工厂返回的是"协议类型"
    reranker=get_reranker(settings),
    llm=get_llm(settings))

⚠️ 修正一句话：不是"所有外部依赖都要抽"

本项目里文件系统就没有抽适配器——loaders / vectorstore 是直接用标准库的：

path.read_text(encoding="utf-8")                  # loaders 直接读
np.save(self._index_dir / _vectors_file, ...)     # vectorstore 直接写

为什么这样没问题？因为它是标准库、几乎不会换、也没有第二个实现。所以"把外部依赖收进适配器"是一条方向，不是教条。

什么时候才值得抽？问三个问题

问题如果答案是"会/有"
它会不会变？会变 → 考虑抽
会不会有第二个实现？（测试替身也算）会有 → 值得抽
有没有外部怪癖？（协议不同 / 会失败 / 要花钱）有 → 该抽

三问皆"否" → 别抽。反例就在项目里：chunking.py 是个纯函数（输入文本、输出片段），不碰网络也不碰磁盘，给它套一层协议没有任何收益，只多一层跳转。

那文件系统什么时候该抽？

当你要支持多个后端（本地磁盘 / 对象存储 OSS / 数据库），或者要在测试里换成假的（不写真实文件就能测存储逻辑）时，就定义 StorageProvider（put / get / exists / list / delete），让 loaders / vectorstore 改成依赖它——套路和现在三个模型适配器一模一样。

外部世界会变 · 会挂 · 有怪癖 · 要花钱
↓ 被"适配器"包住，怪癖关在里面
适配器翻译形状 / 参数 / 返回值 / 异常 / 消化失败
↓ 工厂决定"用哪一个实现"
工厂 get_xxx()换实现只改这一处
↓ 只暴露"协议"约定的形状
调用方（pipeline / api）只认协议，不认识外部世界

练习 E · 用替身跑通上层（省掉最贵的一步） 
class FakeLLM:
    def chat(self, messages, temperature=None) -> str:
        return "这是测试答案，引用 [1]。"

pipeline = RAGPipeline(settings, store, get_embedding_provider(settings),
                       get_reranker(settings), FakeLLM())   # ← 只换了这一个参数

print(result.answer, result.citations)      # 测试答案 + 引用列表
观察两点：① pipeline 一行都没改；② "生成"这一步一次网络请求都没发。 这就是"依赖协议而不是依赖实现"给你的直接好处——慢的、贵的、不稳定的那一环，可以随时换成形状一致的替身。
（检索那一步仍会真调 embedding，用来拿到候选；想完全不联网，可以再给 embedder 写一个"返回固定向量"的替身。）
