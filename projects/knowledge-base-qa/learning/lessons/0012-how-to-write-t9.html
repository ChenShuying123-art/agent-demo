课程 0012 · RAG 项目实战 · 对应任务 T9

把提示词和模型接进链路

T9 是 RAG 第一次端到端跑通：问题进去，带引用的答案出来。而这一课最值钱的一点，藏在一个看起来很普通的函数里——`answer_all_styles` 为什么不能简单地循环调用 `answer`？

学完你能做到：看懂"只检索一次"背后的实验公平性；理解引用编号是怎么从答案文本反查回原文的；并知道为什么"越界引用"要告警而不是崩溃。
配套：术语表 · 前置 课程 0010 / 课程 0011

一、先看一个"想当然"的写法

要让三种风格并排回答，最顺手的写法是：

def answer_all_styles(self, question, styles, doc_ids):
    return [self.answer(question, style, doc_ids) for style in styles]   # ← 有问题

读起来完全合理。但它有个隐蔽的毛病：`answer` 内部会重新检索一次。于是三种风格各自拿到了一份不同的参考资料。

后果 评测时你看到"三种风格分数不同"，但这个差异里混进了两个来源：提示词风格 + 检索运气。 你没法判断是哪个造成的——这一轮实验白做。

这就是课程 0010 讲的"控制变量"，只不过上次它出现在提示词字符串层面，这次出现在编排流程层面。同一个原则，会在不同层反复出现。

二、正确的写法：只检索一次

def answer_all_styles(self, question, styles, doc_ids):
    candidates, used = self.retrieve(question, doc_ids)      # ← 只做一次
    retrieve_ms = ...
    return [self._generate(question, s, candidates, used, retrieve_ms) for s in styles]
    #                    └────────── 同一份参考资料 ──────────┘
问题同一个问题
↓ retrieve()：只做一次
candidates(20) + used(4)三版共用这一份资料
↓ 同一份 user 消息，配三种不同的 system 消息
strict_citation严谨引用型
concise_assistant简洁助手型
socratic_guide引导启发型
↓ 各自调用 LLM
三份答案差异只可能来自 system prompt
图 1 · 一次检索、三次生成——把"检索"这个变量钉死

顺带一个细节：三版的 `latency_ms` 都算上同一份检索耗时，但不互相叠加。

latency_ms = retrieve_ms + generate_ms
#            ↑ 由调用方传入的同一份   ↑ 各自生成自己的

如果每版都自己从零计时，第二、三版就会把前面几版的生成时间也算进去，数字失去可比性。

三、引用是怎么"反查"回原文的

模型只会在答案里写 `[1]`。要变成前端能点开的链接，得反查：

引用编号 n  →  used[n - 1].chunk  →  f"{filename}#{index:04d}"  →  "spec.md#0126"

为什么是 used[n-1]？因为 `format_context` 就是按 `used` 的顺序编的号——这张对照表的两边必须同源。这也是课程 0010 强调"编号绝不能排序去重"的原因。

越界引用：告警，但不崩溃

if not 1 <= number <= len(used):
    logger.warning("答案出现越界引用 [%d]，参考资料只有 %d 条（疑似编造）", number, len(used))
    continue
处理方式后果
抛异常中断用户拿不到答案——为了一个引用标记牺牲整个回答，不划算
悄悄改成 [4]把幻觉洗白了：明明是编造的引用，改完看起来完全正常
忽略 + 告警（本项目）答案照常返回；同时留下痕迹，供评测环节统计"幻觉引用率"

"忽略但不沉默"是处理模型不可靠输出的一条通用思路：不要让一个小瑕疵毁掉整个输出，但也绝不让它无声无息地过去。

四、实测：三种风格真的不一样

问题："召回和重排有什么区别？各自的取舍是什么？"（三版看到的参考资料完全相同）

风格形态引用数耗时
strict_citation4 条分点 + 结尾「依据来源」行28242ms
concise_assistant一句话，无格式13276ms
socratic_guide「结论 / 依据 / 延伸思考」三段 + 追问收尾38671ms

看实际输出的差别有多大：

【concise_assistant】
召回关注召回率（该找到的有没有找到），重排关注准确率（找到的有多准）；
两阶段分别取舍为召回20条以保障覆盖，重排至4条以提升精度 [1]。

【socratic_guide】
【结论】召回阶段侧重广度与覆盖性……而重排阶段侧重精度与排序质量…… [1]
【依据】参考资料[1]明确指出……同时，T8验收要求中强调…… [3]
【延伸思考】既然召回率和准确率存在天然权衡，那么当领域从通用文本切换到
知识图谱问答（KBQA）时，是否应调整召回数量（如从20改为50）？……
现有资料未说明参数调优依据——这属于需补充实验验证的部分。

注意最后一版：它主动承认"这部分资料没覆盖"，而不是编一个答案。这正是硬约束第 2 条在起作用。

五、拒答测试：硬约束真的生效了吗？

问一个资料里完全不存在的问题："珠穆朗玛峰的海拔是多少米？"

风格输出
strict_citation"根据现有资料无法回答该问题。资料未覆盖的部分：珠穆朗玛峰的海拔高度。"
concise_assistant"根据现有资料无法回答该问题。"
socratic_guide三段结构保留，「结论」段直接说明资料不足以回答
这一条为什么重要 RAG 最容易翻车的地方不是"答不出来"，而是"答得太顺"——模型调用自己的常识，流畅地编一段。 三版都拒答、且没有出现任何具体数值，说明"只依据资料作答"这条硬约束真的被遵守了。

⚠️ 一个值得记下来的真实观察

打印最终 messages 时发现：**参考资料里出现了残缺的 markdown 表格行**，比如一整条只剩 | 召回率（该找到的有没有找到）与准确率… |。

原因是 `chunk_size=500` 的硬切把表格从中间截断了。这不是 bug，是切分策略的固有代价——但它提醒我们：

  • T12 出题时，尽量避开表格密集的段落（否则题目依赖的是残缺上下文）；
  • T13 复盘时，如果发现某些题目效果差，回头看看是不是切分把语义切碎了。
