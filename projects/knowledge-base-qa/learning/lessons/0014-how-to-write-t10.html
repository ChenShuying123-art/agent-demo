课程 0014 · RAG 项目实战 · 对应任务 T10

把 RAG 接上网

前 9 个任务里，RAG 只能在 Notebook 里被"你自己"调用。T10 给它套上 HTTP 接口，从此浏览器、Vue 前端、任何程序都能调它。这一课最值钱的一句话是——接口层要薄：它只会做三件事，解析、委托、翻译。

学完你能做到：说清"一句 HTTP 请求是怎么走到 RAGPipeline 的"；看懂为什么接口要单独定义一套"请求/响应模型"而不是直接吐内部对象；知道错误为什么要包成统一形状；以及为什么"Web 版的依赖注入"是把对象挂在 app.state 上。
配套：FastAPI 用法手册 · 术语表 · 前置 课程 0012 / 课程 0013

一、这一层到底在干嘛：一条链路的全程

先建立整体图景，再抠细节。一个请求从进到出，只经过四段：

浏览器 / Vue / curl发一句 POST /api/qa
↓ HTTP
api/routes.py 的路由函数解析请求 → 转成参数
↓ 调用（不做算法）
RAGPipeline召回 → 重排 → 生成（前 9 个任务写的）
↓ 返回 QAResult
响应模型 → JSON翻译成前端能读的形状
图 1 · 接口层是"翻译官"，不是"干活的人"

把路由函数想象成公司前台：它不生产任何东西，只负责把你领到正确的部门（委托），再把你的话翻译成对方能懂的话（翻译）。真正干活的是 RAGPipeline。

薄接口层 路由里不该出现检索、拼提示词、算余弦相似度这类代码。一旦写进去： ① Notebook 和 API 会各持一份逻辑，迟早不一致；② 换框架（比如从 FastAPI 换成别的）时所有业务要重写。 判断标准：把 FastAPI 整个删掉，kbqa/ 里的东西应该还是完整的。T10 正是按这个标准做的——只新增 api/，没动 kbqa/ 一行。

二、路由：把函数"挂"到一个 URL 上

所谓"接口"，在 FastAPI 里就是一个贴了装饰器的普通函数：

router = APIRouter(prefix="/api", tags=["kbqa"])

@router.get("/health", response_model=HealthResponse)   # ← 贴上去，就"挂"在了 GET /api/health
def health(request: Request) -> HealthResponse:
    ...

装饰器 @router.get(...) 做的事，和 @dataclass 一样——替你加工：它把 health 这个函数登记进一张"URL → 函数"的对照表。请求进来时，框架查表、找到函数、调用它、再把返回值变成 JSON。

HTTP 方法语义本项目用在哪
GET读取，不改变数据查健康状态、列文档
POST提交数据、触发一次动作上传、索引、检索、问答
DELETE删除删文档及其向量

三行 /api/documents 里藏着两种方法：POST 是"传一个文件上来"，GET 是"把列表给我"。同一个 URL、不同方法 = 不同动作，这是 HTTP 的约定。

状态码：用数字说"结果如何"

函数要么正常返回，要么抛异常。但 HTTP 需要一个数字告诉调用方"刚才发生了什么"。本项目用到的几个：

码含义本项目什么时候出现
200成功一切正常
400你给的数据有问题doc_id 不存在、风格拼错
404找不到删除一个不存在的文档
422请求体格式不合规漏传 question 字段
502不是我的错，是上游挂了百炼返回 key 无效 / 额度不足
400 与 502 的区别 400 是"你的错"（改一下请求就能成功）；502 是"背后服务的错"（我们的代码没问题，是百炼那边拒绝了）。 分清楚这个，排查时才知道该改前端传参、还是去查 API Key。

三、两套"模型"：为什么接口不直接吐内部对象

项目里其实有两套数据结构描述同一件事：

kbqa/models.py        @dataclass Document   # 内部契约（给 Python 代码看）
api/schemas.py        class DocumentOut      # 对外契约（给网络/前端看）

看起来是"重复定义"，但它们是故意分开的。用两个真实差异来看为什么：

字段内部的 Document对外的 DocumentOut为什么不一样
路径path: Pathpath: strJSON 没有"路径对象"这种类型，得转成字符串
耗时pipeline 返回 elapsed_ms接口返回 ms§8 表格规定对外字段名是 ms，映射在接口层完成

于是接口层多了一排"翻译函数"，名字都以 to_ 开头：

def to_search_out(item: SearchResult) -> SearchResultOut:
    return SearchResultOut(chunk=to_chunk_out(item.chunk), score=item.score, rank=item.rank)

它们像"出口报关"：内部的字段名/类型可以自由演进，只要报关单（schema）不变，前端就不受影响。反过来，API 若要改字段名，改动也只集中在这一个文件里。

顺带白拿的好处：请求校验 请求模型 class QARequest(BaseModel): question: str ... 会自动校验：漏传 question → 框架直接返回 422，函数体根本不会被执行。 再加上 FastAPI 会读这些模型自动生成 /docs 页面——你写的类型注解，变成了可点的接口文档。

四、错误也要有"形状"：统一信封

如果每个接口出错时各返回各的样子（有的是字符串、有的是 {"detail": ...}），前端就得写一堆 if。§8 定的规矩是所有错误一个形状：

{ "error": { "code": "invalid_request", "message": "文档不存在：deadbeef" } }

实现上，路由只管抛异常，由install_exception_handlers集中翻译成这个形状：

抛出的异常翻译成code
ValueError（用户输入非法）400invalid_request
ApiError(404, ...)404document_not_found
RequestValidationError422validation_error
LLMError / OpenAIError502透传百炼的 code（如 invalid_api_key）
其他任何异常500internal_error
为什么 502 要"透传"百炼的 code 上游失败的原因五花八门：Key 写错、没开通模型、账号欠费、地域不对……如果一律回一句"服务异常"，前端只能干瞪眼。 把原始 code 原样带出来（invalid_api_key / Model.AccessDenied），排查时一眼就找到方向。 这就是课程 0008 把 SDK 异常包装成带 .code 的 LLMError 的用处——接口层接住的就是这个 .code。

五、Web 版的"依赖注入"：为什么挂在 app.state

课程 0013 讲过：RAGPipeline 不自己 new 组件，而是从构造函数接住 store / embedder / reranker / llm。那谁来造 pipeline、造完放哪？答案在 create_app()：

def create_app() -> FastAPI:
    store = VectorStore.load(settings.data_dir / "index")     # 1. 造一次
    pipeline = RAGPipeline(settings, store, ...)              # 2. 组装
    app = FastAPI(...)
    app.state.store = store                                   # 3. 挂到 app 身上
    app.state.pipeline = pipeline
    ...
    return app

路由需要时再取出来用：

def _pipeline(request: Request) -> RAGPipeline:
    return request.app.state.pipeline
create_app()只在启动时跑一次
↓ 造出唯一的一份
app.statepipeline + store（应用级单例）
↓ 每个请求通过 request.app.state 取用
路由 A/api/qa
路由 B/api/retrieve
路由 C/api/index
图 2 · 建一次、处处用——这就是"依赖注入"在 Web 里的落地

为什么不用模块级全局变量（像 settings 那样）？因为 pipeline / store 是有状态的对象：

  • 挂在 app.state 上，测试时可以建一个"带替身的 app"，多个测试之间互不污染；
  • pipeline 和 store 必须共用同一个 store 实例——否则会出现"/api/index 往内存索引里写了，/api/documents/{id} 删除时却看不到它"的不一致。

六、两个真实的坑（都写进代码注释了）

坑 1：静态托管要放在路由注册之后

app.include_router(router)                     # 先注册 /api/* 路由
if _WEB_DIST.is_dir():
    app.mount("/", StaticFiles(...))           # 再把 "/" 兜底给前端页面

mount("/") 会抢走所有没被前面匹配的路径。如果先挂它，/api/health 就会被当成"前端静态目录里叫 api 的文件夹"去找，直接 404。

坑 2：写在"上游还没做"的时候

T10 做的时候，T11（Vue 前端）还没开工，web/dist 根本不存在。所以挂载前必须先判断目录在不在：

if _WEB_DIST.is_dir():   # ← 不加这句，T10 阶段启动就报错
    app.mount("/", ...)

这是"按顺序做任务"带来的常见处境：为未来留好接口，但不能依赖未来已经存在。

验收点实测

/api/health 返回三个模型名✅ {"status":"ok","chat_model":"qwen-plus","embedding_model":"text-embedding-v4","rerank_model":"qwen3-rerank"}

不存在的 doc_id → 结构化错误✅ 400 {"error":{"code":"invalid_request", ...}}；DELETE 返回 404 document_not_found
漏字段 / 风格非法✅ 422 validation_error / 400 invalid_request，同一信封
关于"8 个而不是 9 个" tasks.md 的 T10 写"9 个路由"，但 spec §8 的表其实有 10 条，其中 /api/eval/prompt、/api/eval/ablation 依赖 T13 才写的 kbqa/evaluate.py。 本轮只做了其余 8 条，评测两条留到 T13 完成后补挂。 教训：文档里的数字和表格对不上时，以表格（契约）为准，并把差异记下来——不要为了凑数去写还没法实现的接口。
接口层顺带发现的一个上游缺口 GET /api/documents 返回的 indexed 恒为 false、chunk_count 恒为 0。 原因不在接口层，而是 T1 的 loaders.list_documents() 还没去读 T4 建好的 data/index/docs.json（NOTES 里已记为待办）。 接口层的一个好处：它把这类"上游没拼齐"的问题暴露得很清楚——因为前端最需要的就是这些状态。

八、如果从零写这个任务，我的步骤是

  1. 先把 §8 那张表抄成函数骨架：一行 = 一个「方法 + 路径 + 请求 + 响应」，先把名字和返回类型写出来，函数体留 ...。有了骨架，后面只是填空。
  2. 写 schemas.py（请求/响应模型）：请求模型负责校验，响应模型负责形状；再写一组 to_xxx_out() 转换函数。先定契约，再写逻辑。
  3. 写 routes.py 的 8 个函数体：每个都短得可怜——取依赖、调 pipeline、转成响应模型。凡是超过 10 行的路由，八成是把业务写进来了。
  4. 写 create_app() 装配：造 store/pipeline → 挂 app.state → 注册异常处理 → 注册路由 →（可选）挂静态目录。
  5. 最后补统一错误处理：把所有"内部异常"翻译成错误信封。
  6. 按"先离线、后联网"自测：① import 能否通过 → ② /docs 能不能开 → ③ /health → ④ 各种错误路径（不烧钱）→ ⑤ 才跑真正的上传/索引/问答。

第 6 步的顺序很关键：接口层的错误路径全部可以不联网验证（空问题、假 doc_id、漏字段），先把它们跑绿，再花真金白银调模型。

九、能带走的可复用做法

做法什么时候能再用
薄接口层（解析 / 委托 / 翻译）任何 Web 项目。判断标准：删掉框架，核心库依然完整
内部 DTO 与对外 schema 分离 + to_xxx() 转换只要内部结构和对外 API 的演进速度不同，就该这么拆
统一错误信封 {error:{code,message}}前端只需写一套错误处理；上游错误码原样透传
用 app.state（或框架等价物）挂应用级单例有状态对象（连接池、索引、缓存）的标准挂法，测试可替换
"先离线后联网"的自测顺序任何要调用外部付费接口的项目
