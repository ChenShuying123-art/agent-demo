自定义异常与异常处理器

速查表里那句"raise 自定义异常，配合 @app.exception_handler"，其实藏着三个问题：① raise 出去之后谁接住？② 为什么要"自定义"异常？③ @app.exception_handler 这个装饰器到底在干什么？这一课把这三件事一次讲透。

学完你能做到：看懂 class ApiError(Exception) 每一行在干嘛；说清"异常怎么从深层代码一路冒泡到顶层被翻译成 JSON"；并能自己决定——什么时候该定义一个新异常，什么时候用现成的就够。
配套：FastAPI 用法手册 · 术语表 · 前置 课程 0014

一、先把"异常"这个语法补上

异常（exception）是 Python 表达"这件事做不下去了"的方式。用 raise 主动抛出：

raise ValueError("doc_id 不存在")   # 抛出一个 ValueError 对象

抛出去之后会怎样？它会沿着"谁调用了谁"的链条，一层层往上冒，直到有人接住。接住用的是 try / except：

try:
    do_something()          # 这里可能抛错
except ValueError as exc:   # 接住 ValueError 类型的错，取个名字叫 exc
    print("出错了：", exc)

如果一路冒到最顶上都没人接，程序就崩，并打印一大段 traceback。你在终端见到的报错，就是"冒泡到底、无人接住"的样子。

异常对象本身可以带东西 ValueError("一句话") 只是带了一句话。但异常本质是个对象，你可以自己定义一种异常、往它身上挂任意字段—— 这正是本项目 ApiError 干的事：除了消息，还顺手带上 HTTP 状态码和错误 code。

二、反面写法：为什么不让"抛错的地方"自己拼响应

先想清楚"不这么做会怎样"，才明白为什么要这么设计。假设不用异常、也不统一处理，会遇到两种写法，都不好：

# 写法 A：每个路由自己拼错误响应
@router.delete("/documents/{doc_id}")
def delete_document(doc_id, request):
    doc = find(doc_id)
    if doc is None:
        return JSONResponse(status_code=404, content={"error": {"code": "...", "message": "..."}})
    ...   # 每个路由、每个出错分支都来一遍 → 形状迟早漂移
# 写法 B：在深层代码里直接拼 HTTP 响应
# （kbqa/pipeline.py 里）
if doc_id not in available:
    return JSONResponse(404, ...)     # ← pipeline 凭什么知道 HTTP？
问题后果
错误格式散落在各处改一次"信封"要翻很多文件，还容易改漏
深层代码要 import Web 框架的东西核心库被 HTTP "污染"，Notebook 里就不能复用了
出错要靠 return 层层传递中间每个函数都得知道"可能要返回错误"

异常天然解决了第三个问题：抛出去就自动往上冒，中间的函数完全不用管。

三、正解第一步：自定义异常 ApiError

本项目的做法是"只负责抛，不负责长什么样"。先定义一个能携带信息的异常：

class ApiError(Exception):
    def __init__(self, status_code: int, code: str, message: str) -> None:
        super().__init__(message)   # ① 把 message 交给父类 Exception 保管
        self.status_code = status_code   # ② 额外挂三个字段
        self.code = code
        self.message = message
行在干嘛为什么必须这样
class ApiError(Exception)继承内置的 Exception只有 Exception 及其子类才能被 raise；也让框架能统一识别它
super().__init__(message)调用父类的构造函数让异常带着"标准的一句话消息"（str(exc) 能取到，日志里也有）
self.status_code = ...往对象上挂属性这是"自定义"的全部意义：让异常除了消息，还能携带结构化数据

于是抛的时候可以一次带全三种信息：

raise ApiError(404, "document_not_found", f"文档不存在：{doc_id}")

对比一下 raise Exception("文档不存在")：只有一句话，处理器想返回 404 还是 400 都无从判断。自定义异常 = 让错误变成"有结构的数据"。

四、正解第二步：@app.exception_handler 在干什么

异常冒泡到顶层后，框架得知道"这种异常该翻译成什么响应"。办法是提前登记一张对照表——和 @router.get("/health") 登记"URL → 函数"是同一个套路：

@app.exception_handler(ApiError)              # 登记：ApiError 类型 → 下面这个函数
async def _handle_api_error(request, exc):
    return _error_json(exc.status_code, exc.code, exc.message)
路由装饰器异常处理器装饰器
登记表的"键"URL + HTTP 方法异常类型
表里的"值"一个路由函数一个处理函数
什么时候触发请求命中这个 URL异常冒泡到顶层、且类型匹配

完整的一次冒泡过程长这样：

路由函数raise ApiError(404, ...)
↓ 函数里没人 try/except，交给调用它的那一层
FastAPI 路由分发继续往上冒
↓ 还是没有
异常处理中间件查表：ApiError → 哪个处理函数？
↓ 命中 _handle_api_error
返回 JSONResponse(404, {error:{...}})由处理器决定长什么样
图 1 · 抛的人只管"什么错"，长什么样由顶层那张表决定

所以处理器函数的签名是固定的：(request, exc) 进来，Response 出去。你只是"填空"，不用管它是怎么被调用的。

为什么包在 install_exception_handlers(app) 里

def install_exception_handlers(app: FastAPI) -> None:
    @app.exception_handler(ApiError)
    async def _handle_api_error(request, exc): ...

    @app.exception_handler(ValueError)
    async def _handle_value_error(request, exc): ...
    # ... 其余几个

# main.py 里，装配时调用一次
install_exception_handlers(app)

把"一次性注册好几个处理器"打包成一个动作，好处和 T0 的 setup_logging() 一样：规格集中在一处，启动时执行一次。这些嵌套函数能"看到"外面的 app，是因为它们都是在这个函数内部定义的（闭包）。

五、好几个处理器，框架怎么挑？（就近匹配）

本项目注册了 6 个处理器。当异常冒到顶层，框架会沿着这个异常类型的"家族谱系"往上找，谁最具体就用谁：

LLMError(RuntimeError)  →  自己 → RuntimeError → Exception(兜底)
ApiError(Exception)     →  自己 → Exception(兜底)
异常被哪个处理器接住返回
ApiError_handle_api_error用它自己带的 status_code
ValueError_handle_value_error400
RequestValidationError_handle_validation_error422
LLMError / OpenAIError各自的处理器502（透传上游 code）
其他任何异常兜底的 Exception 处理器500
兜底那句 logger.exception 不能省 最后那个 @app.exception_handler(Exception) 会把所有漏网的异常也转成统一信封—— 好处是前端永远拿到同一个形状；坏处是如果不打日志，这个 500 就"静默"了，谁也不知道出了什么事。 所以兜底处理器里必须 logger.exception(...)，把堆栈完整记下来。

六、为什么不直接用 HTTPException？

FastAPI 自带了 HTTPException，一行就能返回错误，确实更简单：

raise HTTPException(status_code=404, detail="文档不存在")   # 响应是 {"detail": "文档不存在"}

但对本项目不够用，原因有三：

问题自定义 + handler 的解法
响应形状是 {"detail": ...}，和我们要的 {"error": {code, message}} 不一样形状在处理器里统一拼，路由不用管
想带 code 这种自定义字段，得往 detail 里塞字典，很别扭自定义异常天生能挂任意字段
深层代码（pipeline）抛的错 根本不认识 HTTP，没法抛 HTTPException抛普通异常（如 ValueError），由顶层翻译

最后一条最关键，它就是课程 0014 讲的"关注点分离"的落地：

# kbqa/pipeline.py —— 核心库，完全不知道 HTTP 的存在
if missing:
    raise ValueError(f"以下 doc_id 在上传目录中不存在：{missing}")

# api/routes.py —— 顶层登记
@app.exception_handler(ValueError)
async def _handle_value_error(request, exc):
    return _error_json(400, "invalid_request", str(exc))
# 于是同一个 ValueError，在 Notebook 里是普通报错，在 API 里是结构化 400
一个类比 餐厅里，服务员（路由）只负责说"这道菜没有了"；至于具体怎么向客人道歉、要不要送一张券，是前台规章（处理器）统一规定的。 服务员不需要知道规章细节，规章改了也不用去培训每个服务员。

八、反例：别过度使用

自定义异常很好用，但别给每种小情况都造一个类，否则会得到一堆没人记得住的异常名。

该自定义用现成的就够
需要携带额外字段（如 status_code / code）只是"值不合法" → ValueError
需要被单独翻译成不同响应只是"找不到文件" → FileNotFoundError
需要让调用方按类型分别处理框架已经抛好的（如 RequestValidationError）

本项目只自定义了一个 ApiError（在 T6 里还定义了带 code 的 LLMError）——关键是"信息量不够"或"翻译方式不同"时才新建，别为了好看而堆砌。
