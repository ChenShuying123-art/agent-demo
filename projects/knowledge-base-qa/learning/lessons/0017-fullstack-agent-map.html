课程 0017 · 项目收束 · 覆盖 T0–T11

从零到全栈：一张地图

前面 16 课，你已经把每个零件单独写过一遍了。这一课不再讲新语法，而是把它们拼成一张地图：一次提问从浏览器出发、绕一圈回到你眼前，中间经过了谁、每层只负责什么、以及"全栈 + Agent 开发"到底在做什么。

学完你能做到：对着这张地图说清每个文件的职责与数据流向；解释"为什么必须先写底层再写接口"；把那几条贯穿全程的工程原则（薄层、依赖注入、统一错误、可观测、控制变量）套用到下一个项目上。
配套：术语表 · FastAPI 用法手册 · 前置 课程 0014 / 课程 0016

一、全景图：一次提问的完整旅程

先建立整体图景。你在页面上敲一个问题、点"提问"，到答案出现，中间发生的事是这样的：

↓ fetch POST /api/qa {question, style, use_rerank}
api/routes.py 的路由函数校验请求体 → 取出 pipeline → 委托
↓ pipeline.answer(question, style, doc_ids, use_rerank)
pipeline.retrieve()召回 20 → 重排 4
embeddings问题 → 向量
vectorstorecosine 取 Top-20
rerank精排取 Top-4
↓ pipeline._generate()：prompts 组装 messages
llm（百炼 qwen-plus）生成答案
↓ 抽取 [n] 引用 → 装配 QAResult
schemas 转成 JSON → 回到浏览器AnswerCard 渲染答案 + 引用 + 召回→重排面板

左侧一列是"阶段"，中间是"谁做"，右边是"怎么看见"。整份 spec 与整个项目，本质上就是在回答这三列。

二、三层架构：每一层只做一件事

项目目录看着多，其实只有三层，边界很清楚：

层目录职责它认识谁
能力库kbqa/加载 / 切分 / 向量 / 检索 / 重排 / 生成 / 编排 / 评测不认识 Web（Notebook 里也能跑）
接口层api/把能力接上 HTTP：解析、委托、翻译认识 HTTP 与 kbqa
前端web/可视化与交互，把两阶段检索画出来只认识 /api/*
一个判断标准（很实用） 把 FastAPI 整个删掉，kbqa/ 里的东西应该还是完整的；把 Vue 删掉，api/ 也照样能用 curl 调。 任何一层被删掉就活不下去，说明层没分开。本项目三层都是能独立跑的——这就是"薄层"的落地。

为什么值得这样分？因为三层的"变化速度"不一样：

  • 换模型（qwen-plus → 别的）：只动 kbqa/llm.py + .env；
  • 换框架（FastAPI → 别的 Web 框架）：只动 api/；
  • 换界面（换个前端）：只动 web/。

分开的理由不是"好看"，而是把变化关在一个盒子里。

三、为什么是这个开发顺序

15 个任务的依赖图（spec §2）看着像流程，其实是一条很有讲究的施工顺序：

T0 骨架配置 / 模型 / 日志
↓ 先把"地基"写稳，后面所有模块都要 import 它
T1–T4 索引链路加载→切分→向量→存储
T6–T7 生成侧LLM 调用→提示词
↓ 底层能力各自可验证后，才开始"串起来"
T5 重排精排
T8 检索编排召回+重排
↓ 编排层是"只做顺序与边界"的薄层
T9 问答编排把检索 + 提示词 + 生成接起来
↓ 核心链路跑通后，才往外包壳
T10 APIHTTP 薄层
T11 前端可视化
图 2 · 由内而外：地基 → 零件 → 编排 → 外壳
核心道理：先能单独验证，再谈集成 越底层越不变、越上层越常变；底层错了，上层做得再漂亮也是错的（tasks.md 里叫"复利增长的排查成本"）。 所以每一层都有独立的验证手段：写 embeddings.py 时用 15 条带编号的文本验顺序，根本不需要前端；写前端时后端已经稳了，出错就只可能是前端。

反例：如果先写前端、边写边补后端，你会陷入"页面不对到底是哪一层的问题"的泥潭——一次只能有一个变量在动（这条原则后面还会出现，就是"控制变量"）。

四、每一层用什么工具验证

层验证工具能测什么不能测什么
能力库Notebook / python -c切分、向量、检索、重排、生成的全部数值HTTP 行为
接口层TestClient / curl / /docs状态码、错误信封、字段形状（不必开前端）页面长什么样
前端浏览器（Vite dev / 单端口）交互、布局、召回→重排面板是否直观底层算法对不对

一个实用习惯：接口层的错误路径几乎都能"离线"测（空问题、假 doc_id、漏字段），先跑绿这些，再花真金白银调模型。

五、贯穿全程的七条工程原则（这是最该带走的）

原则本项目怎么做一句话记忆
配置外置 + fail fast密钥/模型名/参数全在 .env；缺失就启动即报错改配置不改代码，错了立刻炸
依赖注入 + 工厂 + 协议RAGPipeline 接住 store/embedder/reranker/llm；get_*() 决定用哪个实现不自己 new，变化关进一个盒子
薄层 / 关注点分离路由只做解析、委托、翻译；核心库不认识 HTTP删掉框架，库里还完整
统一错误 + 透传上游所有错误都是 {error:{code,message}}；502 带百炼原始 code错误也有形状，排查一步到位
可观测性主流程日志打点（§18.2）；召回/重排分阶段暴露；前端画"召回→重排"中间产物要能看见，别靠猜
控制变量三种风格共享同一份硬约束；answer_all_styles 只检索一次一次只让一个东西变
不变量断言npy 行数 == jsonl 行数；text[start:end] == chunk把"必须永远成立"写成检查

这七条不是 RAG 专属——它们是你做任何后端/全栈项目都能直接搬走的。

六、Agent / RAG 特有的心智模型

1. 检索是"找到证据"，不是"搜索"

普通搜索返回链接给人看；RAG 的检索是给模型递证据。所以评价标准不是"搜得准"，而是"证据够不够支撑答案"——召回宁多勿漏（20 条），让重排去挑（4 条）。

2. 为什么要两阶段检索（召回 20 → 重排 4）

召回（Bi-encoder）重排（Cross-encoder）
做法问题与文档各自编码，比向量距离问题与文档拼在一起过模型打分
速度快（可预计算索引）慢（每条都要现算）
精度粗（区分度窄）细（区分度宽）
角色广撒网，保证不漏精挑，把对的顶上来

这就是"用便宜的方法筛掉 99%，用贵的方法精算 1%"这个通用套路在 RAG 里的样子。

3. 提示词就是"接口契约"

三种风格的差异只在风格段，硬约束是同一份字符串——这让"风格"成了唯一变量。硬约束里的四条（只依据资料、不足则拒答、必须标引用、不许编造）直接决定模型行为，所以它们被冻结在 spec §12.3，代码逐字照抄。

4. 幻觉与拒答是一等公民

RAG 最容易翻车的不是"答不出"，而是"答得太顺"——用常识编一段。所以：越界引用只告警不崩溃、资料外问题必须拒答、追问要承认"资料未覆盖"。

5. 没有评测，就没有 RAG 工程

改切分、换模型、开关重排，凭感觉都是"好像好一点"。所以要：自己出题 → 固定变量 → LLM 当裁判 → 出对比表。评测集必须你自己出（T12 之所以标 👤，就是因为"出题人已知答案，才能判断裁判打分是否靠谱"）。

七、前端这一层（全栈的另一半）

前端只有两种运行形态，记住这张图就不会踩坑：

开发模式Vite :5173 ——proxy /api→:8000—— FastAPI :8000
生产模式FastAPI :8000 同时发页面与 /api（同源）
图 3 · 开发要"热更新"，生产要"一个端口"——所以有了两种形态

四条前端侧的通用做法：

  • 网络调用收在一个文件（api.ts）：组件里不散写 fetch，错误信封也只解包一次；
  • 组件只发事件、不干活：App 当"薄控制器"统一管 loading/错误/刷新，组件是展示型；
  • 契约跟着后端走：api.ts 里的类型与 schemas.py 一一对应，改字段两边同步；
  • 把"最有学习价值的东西"做成一等公民：本项目是「召回 → 重排」面板——如果 UI 不展示它，两阶段检索就白做了。

九、如果让你从零做一个类似项目，步骤是

  1. 先画三层与数据流：能力库 / 接口层 / 前端，各写一句职责。边界不清就别动手。
  2. 列依赖顺序，从"最底层且最不变"的开始写：配置 → 数据结构 → 各能力 → 编排 → 接口 → 前端。
  3. 每写一个模块，配一条验证命令（Notebook 数值 / TestClient 状态码 / 浏览器交互）。验证不通过不往下走。
  4. 把外部依赖都收进适配器 + 工厂：模型、网络、文件系统都一样——换实现只改一处。
  5. 核心链路先用脚本跑通（Notebook/CLI），确定"能出正确答案"了，再包 HTTP。
  6. 接口层只写三件事：解析请求、委托 pipeline、翻译响应；错误统一信封 + 透传上游 code。
  7. 前端把"最有价值的过程"可视化，而不是只显示最终结果。
  8. 最后做评测：自己出题 → 固定变量 → 出对比表 → 按"切分/召回/重排/提示词"归因。

把 data/、.env、learning/、samples/ 这类"运行时数据 / 私人材料"提前写进 .gitignore，也是第 1 步就该做的事。
