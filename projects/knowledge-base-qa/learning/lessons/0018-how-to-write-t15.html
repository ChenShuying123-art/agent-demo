课程 0018 · Agent 化实战 · 对应任务 T15

给模型一张"工具说明书"

T15 不实现任何具体工具，只做三件事：描述工具、登记工具、把工具翻译成模型看得懂的说明书。这一层看起来"没什么业务逻辑"，但它决定了后面 agent loop 能不能用同一种方式调用任意工具。

学完你能做到：解释 Callable[[dict], ToolResult]；看懂 @tool 装饰器如何把函数变成 Tool；说清"模型看到的 schema"和"Python 函数"为什么是两回事；并亲手跑通注册表的四条验收。
配套：术语表 · 前置 课程 0017

二、先补语法：Callable

Callable 是类型注解里表示"可调用对象"的类型。函数、lambda、实现了 __call__ 的对象，都算。

from collections.abc import Callable

def add(a: int, b: int) -> int:
    return a + b

# 读作：接收 int、int，返回 int 的可调用对象
f: Callable[[int, int], int] = add
写法含义
Callable[[], str]无参数，返回 str
Callable[[dict], ToolResult]接收 1 个 dict，返回 ToolResult
Callable[[int, str], bool]接收 int、str，返回 bool
Callable[..., str]任意参数，返回 str
两个易错点 ① [dict] 是参数类型列表，不是"dict 的列表"；
② 类型注解运行时不做检查，它只服务人和 IDE / mypy。

所以 Tool.handler: Callable[[dict], ToolResult] 的意思是：随便你给我一个函数，只要它吃一个 dict、吐一个 ToolResult 就行。不同工具的函数名和内部逻辑可以完全不同，调用方式却统一成 tool.handler(args)。

三、为什么参数是一个 dict

因为参数来自模型。模型输出的是 JSON 字符串：

{"text": "你好"}

上层把它解析成 Python 的 dict，再交给 handler：

args = json.loads(tool_call.arguments)
result = registry.get(tool_call.name).handler(args)

如果一开始就给每个工具定义不同的函数签名（def echo(text: str)、def weather(city: str, days: int)），registry 就没法用同一行代码调用它们——必须写一堆 if name == ...。统一成 dict，换来的是一个循环就能调度所有工具。

四、模型看到的世界：JSON Schema

Tool.parameters 是手写的 JSON Schema，描述参数长什么样。例如 echo：

{
  "type": "object",
  "properties": {
    "text": {"type": "string", "description": "要回显的文本"}
  },
  "required": ["text"]
}

registry.schemas() 把它翻译成 OpenAI tools 格式：

{
  "type": "function",
  "function": {
    "name": "echo",
    "description": "把输入原样返回，仅用于验证注册表。",
    "parameters": { ...上面的 JSON Schema... }
  }
}
字段作用
type: "function"协议固定值，告诉模型这是函数工具
function.name模型点名时用的名字，必须全局唯一
function.description决定模型"什么时候该用它"（其实就是提示词）
function.parameters参数的 JSON Schema，决定模型怎么填参数
为什么不用类型注解自动生成 schema §19.5 要求手写，理由有两条：① 模型看到的就是这份 dict，你可以逐字对照"模型到底看见了什么"；② 不引入额外的 schema 生成依赖与隐式行为。对学习来说，看得见比省事更重要。

五、注册表：一张 dict 就是全部

class ToolRegistry:
    def __init__(self) -> None:
        self._tools: dict[str, Tool] = {}

    def register(self, tool: Tool) -> None:
        if tool.name in self._tools:
            raise ValueError(f"工具名重复：{tool.name}")
        self._tools[tool.name] = tool

三个设计点：

  • dict 保持插入顺序：schemas() 的输出顺序稳定，方便逐字核对。
  • 重名直接 ValueError：如果后注册的覆盖先注册的，模型可能调用到错误的实现，而且一路无错。fail fast 比静默覆盖便宜得多。
  • 只提供 get / names / schemas：本层不执行、不编排、不兜异常。

六、为什么不在这里 try/except

工具执行失败是运行时的正常可能性：网络断了、参数不合法、第三方接口返回错误。T15 的职责只是"登记与查找"，它没有上下文判断"这次失败该不该让整个请求失败"。

职责边界 异常应该由知道下一步怎么办的人处理。agent loop（T18）知道：把异常转成 ToolResult(text="工具执行失败：…")，该步记 ok=False，让模型换个策略继续。所以 T15 原样放行异常，这不是遗漏，是刻意为之。

七、@tool 装饰器逐行看

def tool(name, description, parameters):
    def decorator(handler):
        return Tool(
            name=name,
            description=description,
            parameters=parameters,
            handler=handler,
        )
    return decorator

它其实是"返回装饰器的函数"：

  1. tool(...) 先记住 name / description / parameters，返回 decorator；
  2. Python 把下面的函数作为 handler 传给 decorator；
  3. decorator 返回一个 Tool，原来的函数名就绑定到了这个 Tool 上。

所以下面的 echo 已经不是函数，而是一个 Tool 实例：

@tool(name="echo", description="...", parameters={...})
def echo(args: dict) -> ToolResult:
    return ToolResult(text=args["text"])

registry.register(echo)          # echo 是 Tool，不是函数

1. 数据结构：两份结果，各给谁看

@dataclass
class ToolResult:
    text: str                  # 给模型看的文本（回填前已截断）
    data: dict | None = None   # 给前端看的结构化数据

@dataclass
class Tool:
    name: str
    description: str
    parameters: dict           # 手写 JSON Schema
    handler: Callable[[dict], ToolResult]

为什么是两份：模型只能消费文本，前端需要结构化字段（文件名、分数、坐标）。如果只给文本，前端就得再解析字符串；如果只给 data，模型又读不懂。

2. 注册：dict + fail fast

class ToolRegistry:
    def __init__(self) -> None:
        self._tools: dict[str, Tool] = {}

    def register(self, tool: Tool) -> None:
        if tool.name in self._tools:
            raise ValueError(f"工具名重复：{tool.name}")
        self._tools[tool.name] = tool

    def get(self, name: str) -> Tool:
        try:
            return self._tools[name]
        except KeyError:
            raise KeyError(f"工具不存在：{name}") from None

流程：register 只管登记；get 只管查找。重名不覆盖，因为覆盖会让模型调用到"看起来同名、实际不同"的实现，而且一路无错——这种 bug 最难查。

3. schemas：模型看到的说明书

def schemas(self) -> list[dict]:
    return [
        {
            "type": "function",
            "function": {
                "name": t.name,
                "description": t.description,
                "parameters": t.parameters,
            },
        }
        for t in self._tools.values()
    ]

注意：parameters 原样透传，不做裁剪、不做自动生成。这样你在代码里写的 schema 就是模型实际看到的 schema，可以逐字核对。

4. 装饰器：把函数变成 Tool

def tool(name, description, parameters):
    def decorator(handler):
        return Tool(
            name=name,
            description=description,
            parameters=parameters,
            handler=handler,
        )
    return decorator

执行顺序：tool(...) 先返回 decorator；Python 再把被装饰的函数传给 decorator；最后函数名绑定到 Tool 实例。所以注册时写 registry.register(echo)，echo 已经是 Tool，不是函数。

5. 一次调用的完整流程

  1. 模块导入时，@tool 把每个 handler 变成 Tool；
  2. main.py 调 registry.register(...) 登记；
  3. T18 调 registry.schemas()，随 messages 发给模型；
  4. 模型返回 tool_call(name="get_datetime", arguments='{"date":"today"}')；
  5. T18 解析 JSON → registry.get("get_datetime") → handler({"date": "today"})；
  6. 拿到 ToolResult，把 text 作为 role="tool" 消息回填。

6. 失败路径

情况这一层的行为由谁处理
工具重名ValueError，启动期失败装配方（main.py）
工具名不存在KeyErroragent loop（T18）
handler 抛异常原样放行agent loop（T18）转成 ok=False 的步骤
参数不合法这一层不校验handler 自己返回解释文本

衔接：T15 产出"说明书 + 查找表"；T16 负责把说明书发给模型并解析 tool_calls；T18 才真正把 handler 跑起来。
