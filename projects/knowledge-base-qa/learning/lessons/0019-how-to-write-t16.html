让模型"点名"工具

T15 把工具登记好了，但模型还不会用。T16 只加一件事：让模型能返回"我要调 echo，参数是 {'text': 'hi'}"。注意，模型只负责点名，代码仍然在你的进程里执行。

学完你能做到：看懂 OpenAI 工具调用协议的四种消息角色；解释 ChatResult.content 为什么可能是 None；说清"回填工具结果再调一次"的完整闭环；并理解为什么 chat() 一行都不能改。
配套：术语表 · 前置 课程 0018

一、T16 在做什么

改动内容

chat()一行不改——固定链路还依赖它

二、先补概念：一次工具调用有四种消息

OpenAI 兼容协议里，工具调用不是"一个特殊接口"，而是普通对话消息的一种形态。

role谁写的关键字段
system你content：人格、规则、skill 正文
user用户content：问题
assistant模型content 可选；想调工具时带 tool_calls[]
tool你的代码tool_call_id + content：工具执行结果
user"请调用 echo 说 hi"
↓ 第一次调用
assistantcontent=None，tool_calls=[{id, name:"echo", arguments:'{"text":"hi"}'}]
↓ 你的代码执行 handler({"text":"hi"})，把结果作为工具消息追加
tooltool_call_id=call_xxx，content="hi"
↓ 第二次调用
assistantcontent="hi"，tool_calls=[]，finish_reason="stop"
图 1 · 一次工具调用 = 两次模型调用，中间夹一条 role="tool" 消息
关键理解 模型不会"执行"工具。它只是在 assistant 消息里写了一张调用申请单。什么时候执行、执行几次、失败怎么办，全是你的代码决定的。

三、两个 DTO

@dataclass
class ToolCall:
    id: str          # 回填 role="tool" 时必须带上，用来配对
    name: str
    arguments: str   # 注意：是 JSON 字符串，不是 dict

@dataclass
class ChatResult:
    content: str | None      # 模型只请求工具时是 None
    tool_calls: list[ToolCall]
    finish_reason: str       # "tool_calls" / "stop" / ...

arguments 故意保持字符串，因为解析是调用方的责任：解析成功得到 dict；解析失败按 §19.8 记成 {"_raw": "..."}，交给 loop 处理。

四、请求是怎么发的

request = {
    "model": self._model,
    "messages": messages,
    "temperature": temp,
    "extra_body": {"enable_thinking": self._enable_thinking},
}
if tools:
    request["tools"] = tools

两个设计点：

  • tools=[] 时不传这个字段。部分兼容实现会拒绝空数组；不传就与 chat() 的请求体完全一致，满足"等价"验收。
  • 思考模式仍显式关闭。工具调用叠加思考模式时，tool_calls 更容易解析失败（§4.2 坑 3 的延伸）。

五、响应怎么解析

choice = resp.choices[0]
message = choice.message
content = message.content or None
tool_calls = [
    ToolCall(id=tc.id, name=tc.function.name, arguments=tc.function.arguments)
    for tc in (message.tool_calls or [])
]
finish_reason = choice.finish_reason or ""

注意 message.tool_calls or []：正常回答时这个字段可能是 None，直接遍历会炸。

为什么 content 可能是 None "我要调工具"和"我给你答案"是两种不同的输出。模型选择前者时，content 通常为空，信息全在 tool_calls 里。这不是错误。
但如果既没有文本、也没有工具请求，就说明模型什么都没给——这时才按 empty_content 报错。

六、为什么 chat() 一行都不能改

固定链路 /api/qa、评测、Notebook 全部依赖 chat() 的现有行为。T16 的验收明确要求 git diff 显示它只增不改。

于是新增能力走"加方法"而不是"改方法"：

class LLMProvider(Protocol):
    def chat(self, messages, temperature=None) -> str: ...
    def chat_with_tools(self, messages, tools, temperature=None) -> ChatResult: ...

已有的调用方仍然只认识 chat()，完全不受影响。这是开闭原则的一个具体例子：扩展行为，而不是修改已有行为。

七、日志：参数必须截断

logger.info("工具调用完成 模型=%s 带工具=%d finish_reason=%s 工具调用数=%d 耗时=%dms", ...)
for tc in tool_calls:
    logger.info("工具请求 name=%s 参数=%s", tc.name, _truncate(tc.arguments, 50))

工具参数可能很长（比如把整段文档塞进参数），也可能含敏感信息。按 §18.2：可以打印，但必须截断。这里统一截到 50 字符 + ...。

附：代码全流程拆解

T16 只做一件事：把 messages + tools 发出去，把响应解析成统一的 ChatResult。它不执行工具，也不决定要不要继续循环。

阶段输入输出
① 组装请求messages、tools、temperaturerequest dict
② 调模型requestSDK response
③ 解析response.choices[0].messagecontent + tool_calls + finish_reason
④ 失败判定content 为 None 且无 tool_callsLLMError("empty_content")
⑤ 返回—ChatResult

1. 组装请求：tools 为空就不传

request = {
    "model": self._model,
    "messages": messages,
    "temperature": temp,
    "extra_body": {"enable_thinking": self._enable_thinking},
}
if tools:
    request["tools"] = tools

resp = self._client.chat.completions.create(**request)

为什么 tools=[] 时不传这个字段：部分兼容实现会拒绝空数组；不传也能保证请求体与 chat() 完全一致，行为可预测。

2. 解析响应：模型可能只给工具，不给文本

choice = resp.choices[0]
message = choice.message
content = message.content or None
tool_calls = [
    ToolCall(id=tc.id, name=tc.function.name, arguments=tc.function.arguments)
    for tc in (message.tool_calls or [])
]
finish_reason = choice.finish_reason or ""

content 在工具调用场景经常是 None；arguments 是模型生成的 JSON 字符串，T16 不解析它，交给 T18 执行前再 json.loads。

3. 失败判定：既没文本也没工具

if content is None and not tool_calls:
    raise LLMError("模型未返回 content 且未请求工具", "empty_content")

如果只判断 content is None，正常的工具调用会被误判为失败；如果只判断 not tool_calls，又漏掉空回答。两个条件必须同时成立。

4. 日志：参数必须截断

for tc in tool_calls:
    logger.info("工具请求 name=%s 参数=%s", tc.name, _truncate(tc.arguments, 50))

工具参数是模型生成的，可能很长；日志只保留前 50 字，避免淹没关键信息，也避免把整段用户数据写进日志。

5. 一次调用的完整流程

  1. T18 准备 messages（system / user / 历史 tool 消息）；
  2. T18 调 registry.schemas() 得到 tools；
  3. chat_with_tools(messages, tools) 发请求；
  4. 模型返回 tool_calls → T18 逐个执行；
  5. T18 把每个结果作为 role="tool" 消息 append；
  6. 再次调用 chat_with_tools，直到模型不再请求工具。

6. 失败路径

情况T16 的行为
SDK 抛异常包装成带 code 的 LLMError
空回答LLMError("empty_content")
模型返回多个 tool_calls按原顺序映射成多个 ToolCall
arguments 不是合法 JSONT16 不解析；T18 执行前发现并记 ok=False

衔接：T15 提供 schema；T16 负责"发和收"；T18 才是"看到 tool_calls 后怎么办"。
