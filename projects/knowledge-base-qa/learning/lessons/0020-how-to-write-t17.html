课程 0020 · Agent 化实战 · 对应任务 T17

给模型两只手

T16 让模型会"点名"，T17 给它两个真能干活的工具：查日期时间和检索知识库。这一课的重点不是"写两个函数"，而是看清工具的三条边界：依赖怎么传、结果怎么格式化、失败怎么返回。

学完你能做到：解释为什么日期要交给代码算；看懂"工具结果编号"与"引用溯源"的绑定关系；说清 `build_kb_tool` 为什么用工厂而不是模块级变量；并亲手跑通四条验收。
配套：术语表 · 前置 课程 0018 / 0019

一、T17 的两个工具

工具文件解决什么问题
get_datetimedatetime_tool.py模型算不准"今天几号、星期几"
search_knowledge_basekb_tool.py把已有 RAG 检索包装成模型可调用的工具

二、为什么日期必须交给代码

大模型的知识有截止时间，而且它没有时钟。"今天几号"这种问题，它只能猜。更糟的是"星期几"——这是语料里通常查不到、又特别容易算错的信息。

工具输出长什么样 
日期：2026-10-18
星期：星期日
时间：11:05:02（查询时刻）
相对今天：今天（+0 天）
四个字段分别回答：哪一天、星期几、现在几点、离今天几天。模型拿到就能直接引用，不需要再推算。

三、参数与失败：优先返回文本

{
  "type": "object",
  "properties": {
    "date": {"type": "string", "description": "today、tomorrow 或 YYYY-MM-DD"},
    "timezone": {"type": "string", "description": "IANA 时区名，如 Asia/Shanghai"}
  },
  "required": []
}

两个参数都可省略：默认今天、本机时区。模型给错时（比如 date="下周一"、timezone="北京时间"），工具返回一句解释文本，而不是抛异常：

无法识别的日期：下周一。请使用 today、tomorrow 或 YYYY-MM-DD。
为什么不是直接抛异常 参数错误是"模型可以自己纠正"的错误。把原因作为工具结果回填，模型下一轮就能换成合法参数；抛异常则要等 loop 兜底，模型不一定知道错在哪。
当然，真正的运行时异常（网络、代码 bug）仍然应该抛出去，交给 T18 的 loop 统一处理。

时区怎么处理

用标准库 zoneinfo.ZoneInfo 解析 IANA 名称；不传时区就用本机时区：

if not timezone_name:
    return datetime.now().astimezone()
try:
    return datetime.now(ZoneInfo(timezone_name))
except (ZoneInfoNotFoundError, ValueError):
    return None   # 由调用方转成"无法识别的时区"文本

Windows 上没有系统时区库时，ZoneInfo 可能需要 tzdata 包；本项目默认用本机时区，不引入新依赖。

四、知识库工具：工厂 + 依赖注入

工具需要 RAGPipeline 才能检索。这个依赖不能写死在模块里，所以用工厂：

def build_kb_tool(pipeline: RAGPipeline, max_chars: int = 2000) -> Tool:
    @tool(name="search_knowledge_base", ...)
    def search_knowledge_base(args: dict) -> ToolResult:
        _, used = pipeline.retrieve(query, None)
        ...
写法问题
模块级全局 pipeline应用装配顺序一变就拿到 None；测试时无法注入替身
工具内部自己 new 一个 pipeline重复初始化索引/客户端，配置不一致，测试要真调外部接口
工厂参数注入（本课）依赖显式、可替换、可测试

五、绝不重写检索

工具内部只有一行核心逻辑：

_, used = pipeline.retrieve(query, None)

召回、重排、降级、日志全都在 pipeline 里。工具层如果自己再写一遍检索，会出现两套参数、两套行为，消融实验也就失去意义。

这正是"薄工具层"的含义：工具负责翻译（模型参数 → 现有能力），不负责重新实现能力。

六、编号就是引用契约

返回文本的格式：

[1] 个人知识库验证文档.md#0000（分数=0.9765）
<片段前 300 字>

[2] 个人知识库验证文档.md#0001（分数=0.3678）
<片段前 300 字>
used[0]rerank 第 1 名
↓ 工具输出编号 [1]
模型回答里的 [1]指向 used[0]
↓ 前端/评测按编号反查
用户看到原文可溯源
图 1 · 编号顺序 = used 顺序，绝不能重排

这与 prompts.format_context 的编号规则一致：[n] 永远对应 used[n-1]。工具层只按顺序枚举，不排序、不去重、不跳号。

七、截断：两道保险

  • 单条片段 ≤ 300 字：完整 chunk 可能有 500 字，4 条就会把上下文撑大。
  • 总结果 ≤ AGENT_TOOL_RESULT_MAX_CHARS（默认 2000）：这是 §19.13 的硬上限，超了就截断。

为什么截断放在工具层、T18 的 loop 里还要再做一次？工具层知道自己返回的是什么，可以截得更好看（比如保留每条编号）；loop 的截断是最后一道保险，防止任何工具忘记处理。

八、空库 / 无命中

if not selected:
    return ToolResult(text="未检索到相关资料。")

空库不是错误，是正常结果。模型看到这句话，可以如实告诉用户"资料里没有"，而不是让整个请求失败。

九、日志

工具执行 search_knowledge_base 参数={'query': '...'} 成功=True 命中=2 结果长度=674 耗时=1359ms

按 §19.13，每个工具都要打：工具名、参数（截断）、成功/失败、结果长度、耗时。参数只保留前 80 字符，避免长 query 淹没日志。

附：代码全流程拆解

T17 两个工具的共同目标：把模型给的参数变成可回填的 ToolResult。区别是数据来源——日期用标准库算，知识库复用已有检索。

工具输入核心动作输出
get_datetimedate、timezone解析日期 → 计算星期/相对天数日期 / 星期 / 时刻 / 相对今天
search_knowledge_basequery、top_npipeline.retrieve(query, None)编号片段 + 文件名/分数

1. get_datetime：先解析，再计算

raw_date = str(args.get("date") or "today").strip()
timezone_name = str(args.get("timezone") or "").strip()

now = _now(timezone_name)
if now is None:
    return ToolResult(text=f"无法识别的时区：{timezone_name}。请使用 IANA 时区名。")

today = now.date()
target = _parse_date(raw_date, today)
if target is None:
    return ToolResult(text=f"无法识别的日期：{raw_date}。请使用 today、tomorrow 或 YYYY-MM-DD。")

delta_days = (target - today).days
text = "\n".join([
    f"日期：{target.isoformat()}",
    f"星期：{_WEEKDAYS[target.weekday()]}",
    f"时间：{now.strftime('%H:%M:%S')}（查询时刻）",
    f"相对今天：{_relative_label(delta_days)}",
])

为什么参数错误返回文本而不是抛异常：模型看到"无法识别的日期，请用 YYYY-MM-DD"后，下一轮可以自己改正；抛异常则会让整个 loop 进入失败分支，模型反而拿不到纠正机会。

2. get_datetime：data 给前端

return ToolResult(
    text=text,
    data={
        "date": target.isoformat(),
        "weekday": _WEEKDAYS[target.weekday()],
        "time": now.strftime("%H:%M:%S"),
        "delta_days": delta_days,
    },
)

text 给模型读，data 给前端/日志用；两者内容同源，不会出现"文本说星期一、data 说星期二"。

3. search_knowledge_base：工厂 + 复用检索

def build_kb_tool(pipeline: RAGPipeline, max_chars: int = 2000) -> Tool:
    @tool(name="search_knowledge_base", ...)
    def search_knowledge_base(args: dict) -> ToolResult:
        query = str(args.get("query") or "").strip()
        top_n = _parse_top_n(args.get("top_n"))

        _, used = pipeline.retrieve(query, None)
        selected = used[:top_n]

流程：模型给 query → 工具不自己实现召回/重排 → 直接复用 pipeline.retrieve → 取前 top_n 条。这样工具结果与固定链路看到的是同一套检索结果。

4. 编号：模型引用契约

blocks = []
for number, item in enumerate(selected, start=1):
    chunk = item.chunk
    snippet = chunk.text.strip()
    if len(snippet) > _SNIPPET_CHARS:
        snippet = snippet[:_SNIPPET_CHARS] + "..."
    blocks.append(
        f"[{number}] {chunk.filename}#{chunk.index:04d}"
        f"（分数={item.rerank_score:.4f}）\n{snippet}"
    )

text = _truncate("\n\n".join(blocks), max_chars)

编号顺序 = used 顺序 = rerank 顺序，必须与 format_context 一致；否则模型写 [2] 时，指向的可能是另一段原文。
