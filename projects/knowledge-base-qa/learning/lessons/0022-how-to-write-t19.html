课程 0022 · Agent 化实战 · 对应任务 T19

把 loop 接上 HTTP

T18 的 AgentRunner 只能在 Python 里跑。T19 只做一件事：给它开两个 HTTP 入口，并把内部 DTO 翻译成对外 schema。**路由层不编排、不执行工具、不重写循环。**

学完你能做到：看懂 agent 的请求/响应字段；说清「工具失败」「max_steps」为什么都不是 HTTP 错误；理解 app.state 装配与 TestClient 验证；并能用 curl 跑通完整链路。
配套：术语表 · 前置 课程 0021

二、请求与响应

POST /api/agent/chat
{
  "question": "今天几号？顺便看看知识库里有没有相关约定",
  "skill": null,
  "history": []
}
200
{
  "answer": "...",
  "skill": null,
  "stop_reason": "final_answer",
  "steps": [
    { "index": 0, "tool": "get_datetime", "arguments": {},
      "result_text": "...", "ok": true, "elapsed_ms": 3 }
  ],
  "tool_calls_count": 1,
  "rounds": 2,
  "latency_ms": 1840
}
为什么还要转一层 Out AgentRun 是内部 DTO；AgentRunOut 是对外契约。分两层的好处：内部字段改名不会悄悄改变 API；对外字段也能独立演进。 这和 T10 的 QAResult → QAResultOut 是同一套做法。

三、三类结果的 HTTP 语义

情况HTTP响应
正常结束200stop_reason="final_answer"
工具失败200steps[].ok=false，循环继续
达到步数上限200stop_reason="max_steps"
skill 不存在400{"error":{"code":"skill_not_found",...}}
核心判断 HTTP 错误只表示"这次请求没法处理"。工具失败是 agent 运行过程中的正常分支，最终仍可能给出答案，所以是 200；模型没收敛也是 200，只是 stop_reason 告诉你它没给出最终答案。
只有"请求本身不合法"（如 skill 不存在）才是 4xx。

四、skill_not_found 怎么来的

try:
    run = _agent(request).run(payload.question, payload.skill, payload.history)
except ValueError as exc:
    if payload.skill is not None:
        raise ApiError(400, "skill_not_found", f"skill 不存在：{payload.skill}") from exc
    raise

T18 的 AgentRunner.run 在 skill 非 None 时主动 ValueError（T26 之前没有 skill）。路由层把它翻译成 400；其他 ValueError 仍走全局的 invalid_request。

五、装配：app.state.agent

registry = ToolRegistry()
registry.register(get_datetime)
registry.register(build_kb_tool(pipeline, settings.agent_tool_result_max_chars))
agent = AgentRunner(settings, registry, llm)

app.state.agent = agent

为什么挂在 app.state：

  • 每个应用实例一份，测试可替换；
  • 路由通过 request.app.state.agent 取用，不 import 具体实例；
  • 知识库工具复用同一个 pipeline（也就是同一个 store），避免"索引了却查不到"。

六、路由层要薄

这个路由做了三件事，没有第四件：

  1. 解析请求（pydantic）；
  2. 调用 AgentRunner.run；
  3. 把结果转成响应模型。

它不决定调哪个工具、不执行工具、不写循环。判断标准：删掉 FastAPI，kbqa/agent.py 仍然能独立运行。

八、亲手做一遍

练习 A · curl 跑通 启动 uvicorn api.main:app --port 8010，然后： 
curl -s http://127.0.0.1:8010/api/agent/chat ^
  -H "Content-Type: application/json" ^
  -d "{\"question\":\"今天几号？\"}"
对照响应，找到 steps 里的工具名与耗时。
练习 B · 制造 skill_not_found 请求体加上 "skill": "not-exist"，确认返回 400 与统一错误信封。
练习 C · 看 HTTP 状态码 把某个工具改成必抛异常（或在代码里临时 raise），观察接口仍是 200，但 steps[].ok=false。想清楚：前端应该怎么展示这种"成功响应里的失败步骤"？
练习 D · TestClient 用 fastapi.testclient.TestClient 替换 app.state.agent 为假 runner，断言响应字段。体会为什么把依赖挂在 app.state 让测试更容易。
