课程 0024 · Agent 化实战 · 对应任务 T21

两条路线的对照

固定链路永远检索；Agent 自己决定要不要调工具。T21 用同一批问题把两条路各跑一遍，把「谁调了什么、快不快、答得对不对」摊在一张表里。结果里既有惊喜，也有一个真实的反例。

学完你能做到：设计一个公平的对照实验；读懂「工具选择」与「答案质量」是两件事；并能从一个反例里判断问题出在提示词、工具描述还是模型行为。
配套：术语表 · 前置 课程 0021 / 0022

一、实验设计

变量固定链路Agent
入口pipeline.answer(style="strict_citation")AgentRunner.run
检索必然召回 + 重排模型决定是否调 search_knowledge_base
实时信息无工具，只能拒答可调用 get_datetime
问题集同一批（3 题：事实题 / 实时题 / 事实题）

控制变量：同一个 store、同一个 llm、同一批问题。差异只来自"是否自主调工具"。

二、指标

  • 是否调工具 / 调了哪些 / 步数：看"选择"；
  • 耗时：看成本，但不是公平比较（轮数不同）；
  • 引用数：看可溯源性；
  • 答案是否正确：最终标准。

附：代码全流程拆解

T21 的代码只有三段：装配 → 双跑 → 渲染报告。它不实现检索，也不实现 agent，只负责"公平地跑同一批问题"。

阶段代码产出
① 装配build_components()同一个 store / llm / pipeline / agent
② 双跑pipeline.answer(...) + agent.run(...)每题两行结果
③ 收集rows.append({...})答案、工具、步数、耗时、引用
④ 渲染render(rows)Markdown 表格 + 自动统计

1. 装配：两条路线共用依赖

def build_components():
    store = VectorStore.load(settings.data_dir / "index")
    llm = get_llm(settings)
    pipeline = RAGPipeline(settings, store, embedder, reranker, llm)

    registry = ToolRegistry()
    registry.register(get_datetime)
    registry.register(build_kb_tool(pipeline, settings.agent_tool_result_max_chars))
    agent = AgentRunner(settings, registry, llm)
    return pipeline, agent

关键：pipeline 与 agent 共用同一个 store 和 llm。否则两边的检索结果、模型配置不同，对比就没有意义。

2. 双跑：同一题，两条路

for question in questions:
    fixed = pipeline.answer(question, "strict_citation", None)
    act = agent.run(question)

    rows.append({
        "question": question,
        "fixed_answer": fixed.answer,
        "fixed_citations": len(fixed.citations),
        "fixed_latency": fixed.latency_ms,
        "agent_answer": act.answer,
        "agent_tools": [s.tool for s in act.steps],
        "agent_steps": len(act.steps),
        "agent_latency": act.latency_ms,
    })

固定链路永远走"召回 + 重排 + 生成"；Agent 可能调 0 次、1 次或多次工具。记录工具序列，才能解释答案差异。

3. 渲染：表格 + 数据驱动的案例

for row in rows:
    lines.append(f"| {row['index']} | {row['question']} | 固定链路 | 否 | — | ... |")
    tools = ", ".join(row["agent_tools"]) or "未调用"
    lines.append(f"| {row['index']} | {row['question']} | Agent | ... | {tools} | ... |")

报告不是手写结论，而是从 rows 生成；"本次案例"会自动挑出 get_datetime、未调工具、引用越界等情况，避免只写空泛观察。

4. 指标怎么读

指标说明
是否调工具 / 工具序列看"选择"；固定链路永远为否
步数 / 工具次数看成本与复杂度
耗时不是公平比较：轮数不同
引用数固定链路有结构化 citations；Agent 需从答案 [n] 反推

衔接：T21 对比"固定链路 vs Agent"；T29 再对比"手写 loop vs LangGraph"，方法是同一套。

三、实测结果

问题固定链路Agent
今天几号，星期几？ 检索 10 条后拒答「资料中未提供当前日期」 调 get_datetime，正确回答 2026-10-18 星期日
豆豆的疫苗本编号是什么？ 检索并正确回答 VX-2021-0314-77 [1] 没有调工具，以"隐私信息"为由拒绝回答
2025 年旅行去了哪些地方？ 检索并回答（1 条有效引用） 调 search_knowledge_base，回答正确，但未带 [n] 引用
两个真正的差异案例 ① 实时题：固定链路只能拒答，Agent 换用日期工具——这是"选择"的价值。
② 事实题：Agent 反而没用工具，直接拒答——这是"选择"的风险。 Agent 不是无脑更强，它只是把决定权交给了模型。

四、怎么解释反例

「豆豆的疫苗本编号」在知识库里有明确记录，Agent 却选择不检索。可能原因：

  1. system prompt 没有强调"本地知识库是可信来源，隐私类问题也应先查库"；
  2. 工具描述没有覆盖"个人记录"这类场景；
  3. 模型的安全偏好压过了工具使用倾向。

修法不是"骂模型"，而是把需求写进 prompt / 工具描述，再用同一批问题复测。对照实验的价值就在这里：它把"感觉不太对"变成可定位的问题。

五、耗时怎么看

固定链路平均 2744 ms
Agent 平均      4219 ms

Agent 更慢是正常的：它可能多一轮模型调用、多一次工具执行。不要用"更慢"直接判负——要看它换来了什么（实时信息、少检索、多步推理）。
