课程 0032 · Agent 化实战 · 对应任务 T29

框架到底替你做了什么

T29 是这门课的最后一块拼图：同一批问题、同一套工具、同一个模型，分别用手写 loop 和 LangGraph 跑一遍。结论不是"谁更好"，而是框架替你做了什么、又藏起了什么。

学完你能做到：设计双引擎对照实验；从工具序列、答案、步数、耗时、代码量五个维度读结果；并给出"什么时候选手写 / 什么时候选图"的判断。
配套：术语表 · 前置 课程 0031

一、实验设计

控制变量两版共用
问题集3 题（事实 / 实时 / 事实）
工具同一个 ToolRegistry（get_datetime + search_knowledge_base）
模型同一个 llm 实例与配置
输出契约同一个 AgentRun

唯一变量：handwritten vs langgraph。

附：代码全流程拆解

T29 的代码是 T21 的"双引擎版"：共用依赖 → 两版各跑一遍 → 收集指标 → 渲染差异。它不修改任何一版 loop。

阶段代码产出
① 装配build_components()同一个 llm / registry
② 真实双跑hand.run + graph.run每题两组 AgentRun
③ 边界场景run_max_steps()两版 stop/rounds/steps
④ 渲染render(rows, boundary)Markdown 表格 + 差异

1. 装配：两版共用同一套工具

def build_components():
    store = VectorStore.load(settings.data_dir / "index")
    llm = get_llm(settings)
    pipeline = RAGPipeline(...)

    registry = ToolRegistry()
    registry.register(get_datetime)
    registry.register(build_kb_tool(pipeline, ...))
    return llm, registry

两个 runner 拿到同一个 llm 与 registry，确保差异只来自编排层。

2. 真实双跑：同一题，两个引擎

hand = AgentRunner(settings, registry, llm)
graph = GraphAgentRunner(settings, registry, llm)

for question in questions:
    h = hand.run(question)
    g = graph.run(question)

    rows.append({
        "question": question,
        "hand": h,
        "graph": g,
        "same_tools": [s.tool for s in h.steps] == [s.tool for s in g.steps],
        "same_answer": h.answer == g.answer,
    })

记录工具序列与答案是否一致，而不是只比较耗时；模型采样会让答案有波动。

3. 确定性边界：max_steps

class ScriptedLLM:
    def chat_with_tools(self, messages, tools, temperature=None):
        return ChatResult(None, [ToolCall(..., "get_datetime", "{}")], "tool_calls")

short = settings.model_copy(update={"agent_max_steps": 3})
h = AgentRunner(short, registry, ScriptedLLM()).run("一直调工具")
g = GraphAgentRunner(short, registry, ScriptedLLM()).run("一直调工具")

脚本 LLM 每轮都请求工具，排除模型随机性；两版都应停在 3 轮、2 步，证明控制流等价。

4. 渲染：数据驱动，不手写结论

for row in rows:
    for label, run in (("手写", row["hand"]), ("LangGraph", row["graph"])):
        tools = ", ".join(s.tool for s in run.steps) or "未调用"
        lines.append(f"| {row['index']} | ... | {label} | {tools} | ... |")

if not row["same_tools"]:
    differences.append("- 工具序列不同：...")
if not row["same_answer"]:
    differences.append("- 答案不同：...")

"差异"从数据里自动提取；代码量用 loc() 统计，避免凭感觉说"框架更短"。

5. 指标与结论

维度看什么
工具序列两版选择是否一致；不一致时先怀疑模型采样
步数 / 轮数控制流是否等价
耗时只能作参考，受模型与工具耗时影响
代码量 / 依赖框架的抽象成本与启动成本

衔接：T29 是这门课的终点；它把 T21 的对照方法复用到了"实现方式"层面。

二、实测结果

问题手写LangGraph
豆豆的疫苗本编号 未调工具，回答"需要更多背景信息" 调 search_knowledge_base，答出 VX-2021-0314-77
今天几号，星期几 调 get_datetime，正确 调 get_datetime，正确（两版一致）
2025 年旅行 调检索，回答正确（6466ms） 调检索，回答正确（17297ms）
怎么解释"同一问题工具选择不同" 两版都把决定权交给模型，温度、采样、上下文完全一样也会出现差异。这不是框架 bug，而是 LLM 的非确定性。对照实验要如实记录，不能挑一个"好看"的结果。

三、确定性边界：max_steps

max_steps=3，脚本化 LLM 每轮都请求工具

手写：      stop=max_steps rounds=3 steps=2 tool_calls=2
LangGraph： stop=max_steps rounds=3 steps=2 tool_calls=2
一致性：✅

这是两条实现"行为等价"的证据：控制流被刻意设计成同一套规则，差异只在表达方式。

四、结构与依赖差异

维度手写版LangGraph 版
代码量538 行，显式 while/for264 行，StateGraph + 节点
依赖零框架langgraph（可选安装）
启动不 import langgraph选择该引擎时才延迟导入
可读性逐行可见，适合学习图结构清晰，但需要理解 State/Node/Edge
排查调用栈浅框架层更深，先学框架再排查
扩展加分支要改 if/while加节点/边即可，适合复杂流程

五、结论：不是"谁更好"

  • 学习阶段选手写：你会真正理解"轮数、工具、停止条件"是什么，而不是记住几个 API。
  • 流程复杂后选图：分支、并行、人工介入、持久化、断点续跑，这些用 while 写会迅速失控。
  • 框架的成本：多一层依赖、多一组概念、调用栈更深；它把控制流声明化，也把一部分行为藏了起来。
