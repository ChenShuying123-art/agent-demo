课程 0033 · 概念迁移 · 由 T17 的 build_kb_tool 引出

从一个工厂学会一类问题

你已经看懂了 build_kb_tool(pipeline, max_chars) 这个例子。真正有价值的不是记住它，而是把它提炼成一个可以套用到任何项目上的模板：什么时候该注入、注入点放哪、在哪里装配、怎么用假实现验证。

学完你能做到：拿到任意一个"需要外部依赖"的新功能，按四步判断并写出工厂注入；同时能判断什么时候不该注入，避免为了模式而模式。
配套：术语表 · 前置 课程 0013 · 依赖注入

一、先把这个例子压缩成一行

build_kb_tool(pipeline, max_chars) -> Tool
# 依赖：pipeline（外部资源 / 共享实例）
# 配置：max_chars（会随环境变化）
# 产出：一个 handler 已被闭包绑定好依赖的 Tool

它解决的不是"知识库检索"这个具体问题，而是：如何把一个需要依赖的函数，变成一个签名统一、可直接注册的工具。

二、提炼成通用模板

def build_X(dep_a, dep_b, config=默认值) -> X:
    def handler(args):
        ...  # 用 dep_a / dep_b / config
    return X(handler=handler, ...)
位置作用
参数注入点：外部资源、共享实例、配置
闭包把依赖固定进 handler，之后调用方不需要再传
返回值一个符合统一接口的成品（Tool / Service / Client）

三、四步迁移法

Step 1 · 识别依赖

问自己：这个功能需要什么"不是它自己造"的东西？

  • 外部 IO：数据库、HTTP、文件、模型 API；
  • 共享状态：同一个 store / 同一个 pipeline；
  • 会变的实现：今天用百炼，明天换别的；
  • 测试时需要替换：假 LLM、假时钟、假随机数；
  • 配置：超时、上限、目录、Key。

Step 2 · 选注入点

场景注入方式本项目例子
函数要变成工具 / 回调工厂参数 + 闭包build_kb_tool(pipeline)
一个类需要多个依赖构造函数参数RAGPipeline(settings, store, embedder, ...)
整个应用共用一份应用装配 / app.stateapp.state.pipeline / agent / skills
部署环境不同环境变量 / SettingsDASHSCOPE_API_KEY / AGENT_MAX_STEPS
换实现工厂函数 + 协议get_llm(settings) / get_reranker(settings)

Step 3 · 在组合根装配

组合根 = 唯一允许"自己 new"的地方，通常是 main.py / create_app()：

pipeline = RAGPipeline(...)
registry.register(build_kb_tool(pipeline, settings.agent_tool_result_max_chars))
agent = create_agent_runner(settings, registry, llm, skills)

把创建集中在一处，业务代码只接收成品。这样"谁依赖谁"一眼就能看完。

Step 4 · 用假实现验证

class FakePipeline:
    def retrieve(self, query, doc_ids):
        return [], []

tool = build_kb_tool(FakePipeline())
assert tool.handler({"query": "任意问题"}).text == "未检索到相关资料。"

如果换成"handler 内部自己 new pipeline"，这个测试就必须真的去连模型、读索引——慢、贵、还不稳定。

四、判断表：该不该注入

信号该注入？
会连接外部服务 / 读文件 / 调模型✅ 是
测试时需要替换成假实现✅ 是
多个地方必须共享同一个实例✅ 是
存在第二个实现，或未来很可能有✅ 是
纯函数、只依赖参数❌ 否
标准库小工具、不会变❌ 否
只有一个实现、没有测试需求、也不共享❌ 否（别过度）
一句话判断 这个依赖"会不会变 / 要不要替换 / 要不要共享"——三个问题有一个是"是"，就值得注入；全是"否"，就别抽。

形态代码注入的东西

六、三种常见反面写法

反面写法后果
模块级全局 _pipeline装配顺序敏感、测试互相污染、隐式依赖
handler 内部自己 new重复创建客户端、共享不到同一份索引、测试真调外部
工厂参数无限膨胀build_x(a, b, c, d, e, f, ...) 变成 God Factory；该把一组依赖收敛成一个对象（如 Settings 或上下文）

七、迁移练习（照着四步做）

练习 A · 新增翻译工具 需求：translate(text, target_lang)，调用 LLM，Key 来自配置。
① 依赖：llm、api_key；② 注入点：build_translate_tool(llm, api_key)； ③ 组合根：main.py 注册；④ 假实现：FakeLLM 返回固定译文。
练习 B · 订单通知 需求：下单成功后发邮件。① 依赖：EmailClient；② 注入点：OrderService(notifier)； ③ 组合根：应用启动时创建；④ 假实现：FakeNotifier 记录调用次数，测试断言"发了一次"。
练习 C · 测试 max_steps 需求：验证 AgentRunner 到上限会停。① 依赖：LLM；② 注入点：构造函数； ③ 组合根：测试里直接创建；④ 假实现：ScriptedLLM 永远返回 tool_calls。 这就是项目里 T18/T28 的真实做法。
练习 D · 判断该不该抽 以下三个，哪些值得注入？
① 一个把字符串转大写的纯函数；② 读取当前时间的 now()；③ 发送短信的客户端。
答案：① 不值得；② 值得（测试需要固定时间）；③ 值得（外部 IO + 可替换）。

九、带走这张清单

遇到新功能时，按顺序问四句 ① 它需要什么外部东西？
② 这些东西会变 / 要替换 / 要共享吗？
③ 我该在哪个层注入（函数 / 类 / 应用装配 / 环境变量）？
④ 我能不能用一个假实现，在不连外部服务的情况下测它？
四句都能答上来，工厂注入就写对了。
