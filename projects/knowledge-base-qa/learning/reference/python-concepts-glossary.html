Python 概念术语表

本课程出现过的语法与工程概念，一条一句话。语法属于 Python 语言本身，工程属于"大家都这么干"的惯例。新概念会陆续补进来。

语法

模块（module）语法
一个 .py 文件就是一个模块，文件名（去掉后缀）即模块名。
from X import Y / import X语法
把别处定义的名字拿到当前文件来用。不 import 就用不了，这是"东西从哪来"的入口。
类型注解 name: str语法
说明"这个值应该是什么类型"。运行时不检查，只服务人和工具（IDE、类型检查器）。
Callable语法
类型注解里表示"可调用对象"（函数、lambda、实现了 __call__ 的对象）。写法 Callable[[参数类型...], 返回类型]：Callable[[dict], ToolResult] = 吃一个 dict、返回 ToolResult 的函数；Callable[[], str] = 无参数、返回 str。运行时同样不检查。
默认值 x: int = 10语法
等号后是真正赋值；创建/调用时不给这个值就用它。
类 class语法
把数据和行为打包成的自定义类型。
继承 class A(B)语法
括号里是父类；A 白得 B 的全部能力，再补充自己的东西。
装饰器 @xxx语法
贴在类/函数上、替它"加工"的东西。如 @dataclass 自动生成 __init__。
类属性语法
写在类里、缩进一级的变量，属于类本身而非某个实例。
函数 def f(a, b=1) -> None:语法
def 定义函数；b=1 是参数默认值；-> None 是返回类型。
联合类型 str | None语法
读作"字符串或 None"，表示两种都可能。
关键字参数 f(force=True)语法
按参数名传值，而不是按位置。
docstring语法
写在类/函数第一行的三引号字符串，供 IDE 与 help() 读取。
raise / 异常语法
用 raise 主动抛出"这事做不下去了"的信号。Exception("一句话") 是最基本的异常，本质是个对象，可以往它身上挂任意字段。
try / except语法
接住异常。try 里放可能出错的代码，except 某类型 as exc 接住并处理；没人接就继续往上冒。
运算符重载语法
让自定义类型支持 + - * / 等运算符，做法是实现对应的"双下划线方法"（如 __truediv__）。例：Path("api") / "static" 的 / 走的就是重载，结果是一条路径、不是数值。

工程

包（package）工程
一个文件夹 + 里面的 __init__.py，即可被 import 的包。
import 包 的行为工程
会执行一次该包的 __init__.py。
环境变量工程
活在操作系统里、程序外面的一组键值对，程序可读；用来放会随环境变化的值。
.env 文件工程
本地开发用的 KEY=VALUE 文件，模拟环境变量。绝不提交进 git，仓库只留 .env.example。
配置外置工程
会随环境变化的东西（密钥、地址、模型名）放环境变量，不写进代码。见 12-Factor App（中文）。
fail fast工程
缺关键配置就立刻报错，别带着错配置继续跑。例：密钥字段不给默认值。
JSON Schema工程
用一份 JSON 描述"数据长什么样"的通用格式：{"type":"object","properties":{...},"required":[...]}。模型的工具说明书就用它——模型看得见字段名、类型、说明和必填项，但看不见 Python 函数源码。
注册表（registry）工程
一张"名字 → 实现"的表，运行时按名字查。好处：调用方不需要认识具体实现，新增工具只登记一行。本项目用 dict 实现，重名直接报错，避免静默覆盖。见 kbqa/tools/base.py。
工具（tool）/ tool_call工程
Agent 语境里，tool 是模型可以主动调用的函数；tool_call 是模型输出的"我要调 X，参数是 Y"（OpenAI 协议里是 message.tool_calls[]）。模型只负责点名，真正的代码在你的进程里执行。
finish_reason工程
模型这一轮为什么停下：stop = 正常说完；tool_calls = 想调用工具；length = 被长度限制截断。编排循环靠它判断"该继续还是要结果"。
agent loop工程
「调模型 → 执行工具 → 回填 → 再调模型」的循环，直到模型给最终答案或达到步数上限。外层 while 管轮数，内层 for 管一轮多个 tool_call。见 kbqa/agent.py。
stop_reason工程
agent 为什么停下：final_answer = 模型给了答案；max_steps = 达到轮数上限。它是"正常结束"与"未收敛"的区分标记。
TestClient工程
FastAPI 自带的测试客户端，不用真的启动服务器就能发请求、断言状态码与 JSON。配合 app.state 替换依赖，可以在不烧模型额度的前提下测接口。见 api/routes.py 的验收方式。
props / emits工程
Vue 组件的两个边界：props 是父组件传进来的只读数据，emits 是子组件向父组件发的事件。展示组件只靠这两者工作，不直接发网络请求。见 AgentPanel.vue / ToolTrace.vue。
mock-first / 降级工程
外部依赖还没就绪时，先用明确标注的假数据把链路跑通（mock），并把异常转成可继续处理的文本结果（降级）。关键纪律：mock 必须标注、报告必须写"未联调"，不能把假数据当成真实结果。见 web_search.py / weather.py。
MCP / stdio工程
MCP（Model Context Protocol）是跨进程的工具协议：agent 作 client，工具服务作 server。stdio 传输通过子进程的标准输入输出通信，不需要网络。本项目用它在独立进程里写 markdown。见 mcp_servers/md_writer/ 与 kbqa/mcp_client.py。
失败隔离工程
可选依赖或外部进程失败时，只丢掉这一部分能力，主体继续工作。例：某个 MCP server 起不来 → 只丢该批工具，本地工具与 agent 仍可用。见 register_mcp_tools。
skill / 渐进披露工程
skill = 一段提示词正文 + 一组允许使用的工具。渐进披露：启动只注入 name + description（目录），需要时经 load_skill 加载正文并收窄工具集，避免一开始塞满上下文。见 kbqa/skills.py 与 skills/。
StateGraph / 节点 / 条件边工程
LangGraph 的三个核心概念：State 是共享状态，Node 是处理函数，Edge 决定下一步；条件边根据状态选择分支（如"有 tool_calls 去 tools，否则结束"）。它和 while 循环表达的是同一件事，只是把控制流声明化。见 kbqa/agent_graph.py。
IANA 时区 / ZoneInfo工程
时区的标准命名方式（如 Asia/Shanghai），由 zoneinfo.ZoneInfo 解析。它比 +8:00 更可靠：能自动处理夏令时与历史规则。见 kbqa/tools/datetime_tool.py。
模块级单例工程
在模块末尾创建一次全局对象（如 settings = Settings()），全项目共用，避免配置漂移。
logging工程
标准库，按级别（DEBUG/INFO/WARNING/ERROR）输出信息；比 print 可过滤、可带时间与模块名。
依赖管理工程
用 requirements.txt 记录项目所需的三方库；配合虚拟环境隔离，保证别人能装出一样的环境。
哈希 / sha256工程
把任意长度的内容算成一段定长"指纹"，内容变一点指纹就完全不同。用于校验完整性、做唯一标识。
内容寻址工程
用"内容算出的哈希"当唯一标识，而非文件名/时间。内容相同 → id 相同，天然去重。Git、Docker、网盘秒传都用它。
编码 / UTF-8工程
文本在磁盘上是字节，需要"编码"规则才能读懂。读写文本要显式指定 encoding="utf-8"，否则会跟随系统默认（Windows 上不是 UTF-8，中文会乱码/报错）。
信任边界 / 外部输入不可信工程
来自程序外部的东西（用户上传、网络请求）一律当作不可信，使用前必须校验/消毒。
路径穿越（path traversal）工程
攻击者用 ../../ 之类的文件名让程序把文件写到预期之外的位置。防御：Path(name).name 拍平成纯文件名。
文件元数据 / stat工程
文件的大小、修改时间等由文件系统记录的信息，通过 path.stat() 现取。以磁盘为准，不要凭记忆或参数。
Path（pathlib）工程
标准库里表示"路径"的类。Path("data") 语法上就是调用类造一个对象（和 Settings() 同理），不是特殊语法。好处：跨平台（自动用对分隔符），且把常用操作做成方法——.拼接、.exists()、.is_dir()、.read_text()、.name/.suffix、.glob()、.unlink()。注意 Path("a") / "b" 的 / 是运算符重载，不是除法。见 config.py / loaders.py。
正则表达式（regex）工程
用一套符号描述"什么样的文本片段"。^ 行首、\n 换行、* 零或多次。用于识别空行、标题行这类模式。
不变量（invariant）工程
任何情况下都必须成立的断言，例如 text[start:end] == chunk_text。先想清楚"什么必须永远成立"，再写成检查去跑，比肉眼核对可靠。
断言 assert语法
条件不成立就抛 AssertionError。用来把不变量变成可执行的检查，适合自测与调试。
向量 / embedding工程
模型把一段文本映射成的一串定长数字。语义相近的文本，向量方向更接近。
分批（batching）工程
受接口"单次条数上限"限制，把输入拆成多批依次发送。关键不在"发出去"，而在拼回来的顺序必须与输入一致——顺序错不会报错，只会让结果整体错位。
L2 归一化工程
把向量长度缩放到 1。归一化后"点积 == 余弦相似度"，算起来更快。注意：百炼的 embedding 接口本就返回单位向量（L2 范数 = 1.0），再归一化是安全的空操作。
Top-N / argpartition工程
只要最大的 N 个时不必整体排序：argpartition 用 O(N) 挑出候选，再对选中的 N 个排序（全排序是 O(N log N)）。代价是它不保证挑出的 N 个内部有序。
幂等（idempotent）工程
同一操作执行一次和执行多次，结果相同。例：重新索引前先 remove_document，这样 Notebook 重复运行也不会累积重复 chunk。
终端编码陷阱工程
用管道把含中文的脚本喂给 python - 时，管道会按控制台代码页编码，内容真的会损坏（不只是显示成 ?）。规则：含非 ASCII 的脚本一律写成 .py 文件再运行。
Bi-encoder / Cross-encoder工程
双塔：查询与文档各自独立编码，可预计算、快，但无交互（召回用）。交叉编码器：两者拼在一起过模型，有细粒度交互、准，但无法预计算（重排用）。
协议 Protocol语法
只约定"有哪些方法、什么签名"，不规定怎么实现。业务代码只依赖协议，换实现时不用改调用方（配合工厂函数使用）。
工厂函数（factory）工程
集中对象创建逻辑的函数（如 get_llm(settings)）。换实现只改工厂一处，其余代码不动。
闭包工厂工程
返回"已经绑定好依赖的函数/对象"的工厂。参数是注入点，内部函数通过闭包捕获依赖。例：build_kb_tool(pipeline) 返回的 handler 已经记住了 pipeline。见课程 0033。
组合根（composition root）工程
整个应用里唯一集中创建依赖、完成装配的地方（本项目的 api/main.py / create_app()）。业务代码只接收成品，不自己 new。见课程 0033。
适配器（adapter）工程
把外部依赖的接口与异常"翻译"成自己项目约定的形状（如把 SDK 异常包成带 code 的 LLMError），让业务代码不被外部细节渗透。
思考模式（thinking mode）工程
模型在回答前先输出一段推理过程。部分千问模型默认开启：更慢更贵，且正文可能落到 reasoning_content 导致 content 为空。RAG 场景须传 enable_thinking=False 关闭。
OpenAI 兼容协议工程
OpenAI 的 chat/completions 接口成了事实标准，其他厂商模仿它的 URL 路径、请求字段、响应结构与错误格式。好处：换厂商只改 base_url + model。注意它与 typing.Protocol 不是一回事——一个是网络接口约定，一个是代码内部形状约定。
extra_body工程
OpenAI SDK 留的逃生口：把"兼容协议未覆盖的厂商私有参数"（如 enable_thinking）原样塞进请求体。放在这里的东西，正是"兼容"没覆盖到的地方。
单一事实来源（single source of truth）工程
某份文档 / 文件是唯一的权威版本。例：提示词正文以 spec §12.3 为准，代码必须与它逐字一致，要改先改文档。任何"两处各存一份"的做法迟早会不一致。
控制变量法（control variable）工程
评测时只让一个因素变化、其余全部固定。本项目用"共享硬约束 + 风格段"的代码结构实现：硬约束是同一份字符串，所以三版差异只可能来自风格段。
编排（orchestration）工程
把若干子能力按顺序串成链路，自身不实现具体逻辑（不做 IO、不调模型）。好处：每一环都能单独替换，也能单独观察（见 RAGPipeline）。
依赖注入（dependency injection）工程
不自己在内部 new 依赖，而是由调用方从构造函数传进来。RAGPipeline 接住 store / embedder / reranker / llm 四个组件，所以测试和消融实验都能塞替身或换配置。
幻觉引用（hallucinated citation）工程
答案里标了不存在的引用编号（如只给了 4 条资料却标 [7]）。处理原则：忽略 + 告警——不因小瑕疵毁掉整个回答，也不让它无声无息地溜过去，留待评测统计"幻觉引用率"。
控制反转（IoC）工程
把"用哪个实现"的决定权从模块内部挪到调用方。实现手段就是依赖注入：自己不 new，由外部把组件传进来。
自己 new 工程
在代码里直接写构造函数调用造对象（如 DashScopeChat(settings)）。"new" 是 Java 的说法，Python 里对应构造函数调用。相对的写法是"依赖注入"。
路由（route）工程
把"某个 URL + 某个 HTTP 方法"绑到一个函数上。FastAPI 里用 @router.get("/health") 这类装饰器登记；请求进来时框架查表、找到函数、调用它。
HTTP 状态码工程
用一个数字表达结果：2xx 成功；4xx 是"你的错"（400 参数非法、404 找不到、422 格式不合规）；5xx 是"我这边的错"（502 上游失败）。分清楚才知道该改请求还是查上游。
请求 / 响应模型（schema）工程
接口对外的输入输出结构（本项目用 pydantic 的 BaseModel）。一身两职：校验请求（漏字段直接 422，函数体不执行）+ 自动生成 /docs 接口文档。
错误信封工程
让所有错误长得一样的固定结构，本项目为 {"error":{"code","message"}}。前端只写一套错误处理；上游的原始 code 原样透传，便于一眼定位 key/额度/地域问题。
上游 / 下游工程
一次调用里被依赖的一方叫上游（如百炼模型），发起方叫下游。上游失败一般回 502，而不是 400——因为错不在调用方。
应用级单例（app.state）工程
有状态的对象（向量库、pipeline）在启动时造一次、挂在 app.state 上供各路由共用。比模块级全局变量更好测试、更好替换；注意共享同一实例，否则会出现"索引了却删不掉"的不一致。
异常冒泡 / 调用栈工程
异常沿"谁调用了谁"的链条一层层往上抛，直到被 except 或框架顶层接住。好处：抛出点的中间函数完全不用管，错误自动抵达能处理它的地方。
自定义异常工程
继承 Exception、往对象上挂额外字段（如本项目 ApiError 的 status_code / code）。意义是让"错误"从一句话变成有结构的数据。别滥用：只有"信息量不够"或"需要被单独翻译"时才新建。
异常处理器（exception_handler）工程
用 @app.exception_handler(某异常类型) 登记"异常类型 → 处理函数"的对照表（和路由表登记"URL → 函数"同理）。异常冒泡到顶层时框架按类型就近匹配（更具体的子类优先），未匹配的由 Exception 兜底。见课程 0015。
关注点分离（separation of concerns）工程
让每一层只关心自己那件事：核心库只管抛 ValueError，不必知道 HTTP；接口层只管把异常翻译成响应。表现就是"删掉框架，核心库依然完整"。
入口文件（entry point）工程
服务启动时第一个被加载的模块，负责把零件装配成应用并暴露一个约定的对象（uvicorn 找 api.main 里名叫 app 的变量）。见课程 0016。
import 缓存 / 模块只执行一次工程
模块首次被 import 时执行其顶层语句，之后存进缓存（sys.modules），再 import 直接取缓存、不再重跑。所以写在模块最外层的 app = create_app() 天然只有一份（模块级单例）。
副作用（side effect）工程
一次操作除返回值外，还对外部世界产生了影响（如 import 时就真的加载了索引）。import api.main 是有副作用的——这既是"启动即报错（fail fast）"的手段，也提醒你别随手 import。
静态资源 / 静态文件工程
现成、每次内容都一样的文件（HTML / CSS / JS / 图片），不需要后端计算；相对的"动态接口"会随请求参数或数据变化。前端 npm run build 后产物就是静态文件。
挂载（mount）工程
在某条 URL 前缀上接一个独立的处理程序，该前缀下的请求全交给它（如 app.mount("/", StaticFiles("web/dist", html=True))）。是"一整片区域"，不同于路由的"精确匹配一条 URL"。
分层架构 / 薄层工程
每层只做一类事，层与层靠明确接口沟通。判断标准：删掉某一层，其它层还能独立跑——删掉 FastAPI，kbqa/ 依然完整；删掉 Vue，api/ 依然能用 curl 调。好处是把"变化"关在一个盒子里。见课程 0017。
可观测性（observability）工程
让系统内部状态"看得见"：主流程按 §18.2 打日志、把中间产物分阶段暴露（召回 20 与重排 4 分开返回）、前端把过程画出来（「召回 → 重排」面板）。目的：出问题能定位，而不是靠猜。
消融实验（ablation）工程
把某个组件关掉再跑一遍，看指标差多少，据此判断它是否真的有用（本项目做法：固定提示词，只开关 Rerank）。前提是其它变量全部固定，否则分不清是谁的功劳。
LLM-as-judge（模型当裁判）工程
用大模型给回答打分（对照 expected_points），替代人工评测。风险是"裁判也会错"：所以要记录逐题理由、统计 JSON 解析失败率，并由已知答案的出题人来校准（这就是 T12 必须人工出题的原因）。
