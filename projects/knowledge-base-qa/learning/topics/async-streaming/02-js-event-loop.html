专题 · 02

浏览器事件循环：await 到底排在谁前面

记住三条规则，绝大多数 async/await 顺序题都能手推。下文所有输出都是在 Node v22 实际运行的结果；浏览器在任务/微任务层面的规则相同。

一、三条规则

  1. async 函数被调用时，函数体立刻同步执行，一直跑到第一个 await。
  2. await 把函数挂起，剩下的代码登记成微任务，控制权还给事件循环。
  3. 顺序是：当前宏任务跑完 → 清空微任务队列 → 浏览器渲染 → 下一个宏任务。

二、例 1：同步、微任务、宏任务

console.log('1 脚本开始')

setTimeout(() => console.log('6 setTimeout 0ms'), 0)
Promise.resolve().then(() => console.log('4 Promise.then'))

async function main() {
  console.log('2 main 函数体开始（同步执行）')
  await null
  console.log('5 await 之后的代码（微任务）')
}

main()
console.log('3 脚本结束')
1 脚本开始
2 main 函数体开始（同步执行）
3 脚本结束
4 Promise.then
5 await 之后的代码（微任务）
6 setTimeout 0ms
时刻发生了什么
①console.log('1') 直接执行。
②setTimeout 注册一个宏任务，排队不执行。
③Promise.then 注册一个微任务。
④main() 同步跑到 await null，打印 2，挂起；余下代码成为微任务。
⑤回到脚本，打印 3。
⑥脚本结束，清空微任务：先 Promise.then（4），再 main 的续体（5）。
⑦取下一个宏任务 setTimeout（6）。

注意：await null 后面是现成的值，5 也没有立刻打印——await 一定会让出一次。

三、例 2：await fetch 期间谁在干活

function fakeFetch() {
  return new Promise((resolve) =>
    setTimeout(() => resolve({ json: () => ({ answer: 'ok' }) }), 100)
  )
}

async function load() {
  console.log('A load() 开始（同步）')
  const res = await fakeFetch()
  console.log('C await fetch 之后')
  const data = await res.json()
  console.log('D 解析完成', data.answer)
}

console.log('1 脚本开始')
setTimeout(() => console.log('T 50ms 定时器（等待期间照常执行）'), 50)
load()
console.log('2 脚本结束')
setTimeout(() => console.log('Z 200ms 定时器'), 200)
1 脚本开始
A load() 开始（同步）
2 脚本结束
T 50ms 定时器（等待期间照常执行）
C await fetch 之后
D 解析完成 ok
Z 200ms 定时器
0ms    脚本同步执行：1 → A → 注册 100ms 任务 → await 挂起 → 2
0ms    微任务为空 → 事件循环空闲
50ms   50ms 定时器到点 → 打印 T          ← 网络还没回来，页面/JS 照常干活
100ms  网络回来 → resolve → await 续体作为微任务 → C
100ms  第二个 await 的续体 → D
200ms  200ms 定时器 → Z

这就是 await fetch 不卡页面的原因：等待发生在浏览器内部，主线程在 await 处已经把控制权还给了事件循环。

四、例 3：返回的是微任务吗？

问题来自这段代码：

return new Promise((resolve) =>
  setTimeout(() => resolve({ json: () => ({ answer: 'ok' }) }), 100)
)

返回的是 Promise 对象，不是微任务。这里叠了三层：

代码是什么进什么队列
new Promise(executor)创建 Promise；executor 立即同步执行不进队列
setTimeout(cb, 100)注册一个定时器任务宏任务队列
resolve(value)改状态，并把登记过的反应排进队列反应进微任务队列
await p / p.then(cb)登记一个 reaction兑现后进微任务队列
 
console.log('1 脚本开始')

const p = new Promise((resolve) => {
  console.log('2 executor 同步执行（此刻仍是 pending）')
  setTimeout(() => {
    console.log('4 定时器回调（宏任务）')
    resolve('ok')
    console.log('5 resolve 之后同一段同步代码继续')
  }, 100)
})

console.log('6 new Promise 已返回:', p instanceof Promise)
p.then((v) => console.log('7 then 回调（微任务），值 =', v))
Promise.resolve().then(() => console.log('3 已就绪 Promise 的 then（微任务）'))
console.log('8 脚本结束')
1 脚本开始
2 executor 同步执行（此刻仍是 pending）
6 new Promise 已返回: true
8 脚本结束
3 已就绪 Promise 的 then（微任务）
4 定时器回调（宏任务）
5 resolve 之后同一段同步代码继续
7 then 回调（微任务），值 = ok
  • 2 在 6 前：executor 是同步执行的。
  • 3 在 4 前：已就绪 Promise 的 then 是微任务，先于 100ms 的宏任务。
  • 5 在 7 前：resolve() 只改状态并排队；当前同步代码先跑完，then 才在微任务阶段执行。

六、顺序实测

console.log('1 script')
setTimeout(() => console.log('5 setTimeout（宏任务）'), 0)
Promise.resolve().then(() => console.log('2 promise.then（微任务）'))
queueMicrotask(() => console.log('3 queueMicrotask（微任务）'))
process.nextTick(() => console.log('0 process.nextTick'))

;(async () => {
  await null
  console.log('4 await 续体（微任务）')
})()
1 script
0 process.nextTick
2 promise.then（微任务）
3 queueMicrotask（微任务）
4 await 续体（微任务）
5 setTimeout（宏任务）

同一队列内按登记顺序 FIFO；当前宏任务结束后先清 nextTick 队列（Node），再清 Promise 微任务队列，最后才取下一个宏任务。

容易忽略 微任务里还能产生微任务，事件循环会一直清到队列为空；写不好会饿死渲染和定时器。queueMicrotask 里抛错是全局未捕获错误，不是 Promise rejection。
