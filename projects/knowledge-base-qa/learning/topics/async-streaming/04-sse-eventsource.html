专题 · 04

SSE 事件格式、契约与 EventSource

分两层看：外壳（event: / data: / 空行）是 WHATWG 标准；花括号里的 JSON 和事件名是项目自己定的契约。

一、外壳：SSE 协议

来自 WHATWG HTML Standard 的 Server-sent events 一节，媒体类型 text/event-stream。纯文本行协议：

event: tool_result
data: {"event":"tool_result","index":0,"tool":"get_datetime","ok":true}
                                  ← 空行 = 一条事件结束

event: token
data: {"event":"token","text":"今天是 **20"}
字段作用本项目
data:负载；多行会用 \n 拼接用，一行 JSON
event:事件类型名，默认 message用
id:断线重连游标（Last-Event-ID）没用
retry:重连间隔毫秒没用
: xxx注释行，常做心跳没用

规范细节

  • 流必须是 UTF-8；行尾 \r\n、\n、\r 都接受。
  • 字段名大小写敏感。
  • data: 后面那个空格可有可无，标准会吃掉第一个空格。
  • 空行才触发事件；少一个空行，前端会一直等。
  • data: 行内不能有裸换行；JSON 会把换行转义成 \n 两个字符，正好安全。

后端就是拼字符串（routes.py:289）：

yield f"event: {item['event']}\ndata: {json.dumps(item, ensure_ascii=False)}\n\n"

二、内层：项目自己的契约

JSON 字段和事件名不是标准定的，是项目定的。链条如下：

  1. 规格先定事件名：docs/spec-agent.md:285 写明 step_start / tool_call / tool_result / token / done。
  2. 实现补了 error：routes.py:246 的 docstring 写“失败时 error”。规格里只有 5 种，这是实现阶段扩展，没回写规格。
  3. 字段形状由发事件处决定：agent.py:119、:150 直接构造 dict；tool_result 由 _step_event()（agent.py:408）生成；token / done / error 在 worker 里拼（routes.py:262-279）。
  4. 前端镜像成类型：web/src/api.ts:86-108 是 TS 可辨识联合；App.vue:111-135 按 ev.event 分支渲染。
结论 事件名来自 spec §19.10，字段来自 Python 侧 dict，两端靠人工保持一致，没有 schema 校验。改字段要同时改规格、后端、前端类型、渲染分支。

三、几个设计点

为什么 JSON 里又放了一遍 "event"？

外层 event: 是 SSE 用的，内层 "event" 是业务用的。而这个前端只读 data: 那一行（api.ts:331-333），外层 event: 完全没被使用。它的价值只剩 curl / DevTools 里肉眼可读，以及将来换成 EventSource 时能用 addEventListener('token', ...)。代价是两个真相来源，可能漂移。

为什么用 JSON 而不是纯文本？

SSE 的 data: 不能有裸换行；答案里有 Markdown、可能有换行。JSON 编码把换行转义掉，前端 JSON.parse 一步到位。

done 为什么还带完整 answer？

token 是分片，任何一片丢失都会文字残缺。done 是最终对账：App.vue:126 直接用 ev.answer 覆盖。这就是“增量渲染 + 最终一致”。

index 干什么？

一轮里模型可能同时点多个工具。tool_call 和 tool_result 都带 index，前端才能把结果配回对应调用（AgentStep.index）。

为什么 error 是事件而不是 HTTP 4xx/5xx？

流已经开始时响应头（200）早发出去了，状态码改不了，只能把错误塞进流里。所以前端必须在 onEvent 里处理 error（App.vue:132-134）。

四、EventSource 是什么

SSE 是协议，EventSource 是浏览器自带的 SSE 客户端。不用装库，new EventSource(url) 就能用。类比：

协议浏览器自带客户端
WebSocketnew WebSocket(url)
SSE（text/event-stream）new EventSource(url)
HTTPfetch / XMLHttpRequest
 
const es = new EventSource('/api/agent/chat/stream')

es.onmessage = (e) => console.log(e.data)
es.addEventListener('token', (e) => {
  console.log(JSON.parse(e.data).text)
})
es.onerror = () => console.log('断了，浏览器会自动重连')
// es.close()

它免费提供什么

  • 解析帧：event: / data: / 空行，多行 data 拼接。
  • 按类型分发：event: token 触发 addEventListener('token', ...)。
  • UTF-8 解码与半截块缓冲。
  • 自动重连，间隔由服务端 retry: 控制。
  • 断点续传：服务端发过 id: 时，重连带 Last-Event-ID。

五、为什么本项目不用它

EventSource 只发 GET，不能带请求体、不能加自定义请求头。而接口是：

POST /api/agent/chat/stream
Content-Type: application/json
{"question": "...", "skill": null, "history": []}

所以只能用 fetch + response.body.getReader()，自己读流、切 \n\n、JSON.parse（api.ts:317-334）。

把参数塞进查询串发 GET 也能绕，但：URL 有长度限制、问题内容会进访问日志、中文要编码。POST 更合理。

因此手工补上的东西

EventSource 免费提供本项目手写的位置

UTF-8 流式解码api.ts:322 TextDecoder + { stream: true }

id: 续传没有，服务端也没发 id:

六、这套格式的短板

  • 没有 id:：断线后无法续传。
  • 没有心跳注释行（: ping）：长时间无事件的工具调用，可能被网关按空闲超时掐断。X-Accel-Buffering: no 只解决缓冲，不解决超时。
  • 没有版本号：字段改名时，旧前端会静默解析失败。
  • event 双重出现：两处可能不一致。
