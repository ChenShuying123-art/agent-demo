GET / POST / PUT 的本质区别

要害只有两个词：安全与幂等。其余差别（参数位置、缓存、重试）都是这两个性质的推论。

一、一张表

方法语义参数位置安全幂等典型用途
GET读URL 查询串是是列表、详情、健康检查
POST提交 / 触发处理请求体否否创建、问答、上传、执行动作
PUT整体替换请求体否是按 ID 覆盖整个资源
PATCH局部修改请求体否通常否改一个字段
DELETE删除URL否是删资源

二、两个词

  • 安全（safe）：调用它不改服务端状态。GET 是，其余都不是。
  • 幂等（idempotent）：同一个请求发 1 次和发 N 次，最终状态一样。GET / PUT / DELETE 是，POST 不是。
注意 幂等说的是副作用相同，不是“响应完全一样”。PUT 第二次可能返回 204，但资源状态没变，仍算幂等。

三、三者的本质

  • GET /documents/42：把 42 号文档给我。重发 10 次也不会多出一条数据。
  • POST /documents：交一份新文档，ID 由服务端分配。重发 10 次可能创建 10 份——不幂等。
  • PUT /documents/42：42 号文档的完整新内容就是这个，覆盖旧的。重发 10 次还是同一份内容——幂等。

一句话：POST 是“帮我办件事”，PUT 是“这个位置的内容改成这样”。

这个项目一个 PUT 都没用。如果要支持“用新内容整体替换 42 号文档”，才该是 PUT /api/documents/42。

一个容易困惑的点

POST /api/retrieve、POST /api/qa、POST /api/qa/compare 明明是“查询”，为什么不用 GET？

因为参数是结构化对象（question + doc_ids + use_rerank），放进 URL 又长又丑，还可能超长度限制。GET 放不下参数时，用 POST 做查询是常见妥协，代价是失去缓存和“可安全重试”的语义。理论纯度让位于工程现实。

五、四条实战规则

  1. 能被浏览器缓存、收藏、预取、重放的，只能是 GET。
  2. 会改数据或花钱的，不要用 GET——爬虫和预取会替你点一遍。
  3. 需要重试/重放的写操作，优先设计成 PUT（幂等）；POST 重试要自己做去重（幂等键、请求 ID）。
  4. 局部更新用 PATCH，不要用 PUT 硬凑；PUT 的语义是“整体替换”，少传一个字段就意味着把它清空。

六、常见误区

  • “GET 只能查、POST 只能改”：这是约定，不是协议强制。但违反它会破坏缓存、重试和代理行为。
  • “PUT 和 POST 的区别是 PUT 幂等”：对，但根因是语义不同——PUT 整体替换已知资源，POST 提交给服务端处理。
  • “POST 创建，PUT 更新”：不完整。PUT 也可以创建（客户端指定 ID 时），POST 也可以更新（比如“给文档追加一段”这类动作）。
  • “DELETE 不幂等”：DELETE 是幂等的——删 1 次和删 10 次，最终都是“不存在”，即使第二次返回 404。
