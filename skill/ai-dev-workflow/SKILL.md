# AI 开发工作流

把需求从文档推进到可提交的代码。流程有三个硬闸门：**没澄清完不动手实现，没确认 RoadMap 不动手实现，每个 goal 完成后停下来等人 review**。

## 0. 取需求

优先用环境里可用的 PRD 类 MCP（Jira / Confluence / TAPD / ONES / 内部需求平台等）拉取需求正文、评论、关联工单和设计稿，拿原文而不是摘要。没有可用的 MCP 或拉不到内容时，直接找用户要 PRD 链接或原文，不要按标题猜需求。

## 1. 澄清 → 需求文档

读完 PRD 再对照相关代码，把不理解的、有两种解释的、和现状冲突的地方整理成编号问题，一次性抛给用户；等回答，再追问，多轮进行直到没有阻塞性问题。**这个阶段只提问和写文档，不写实现代码。**

问题要问到"自己通读文档能看懂"为止，复杂需求提几十个问题是正常的。提问策略、覆盖维度和需求文档模板见 [references/01-clarify.md](references/01-clarify.md)。

需求文档是给人看的，不是实现笔记：先自己确认能看懂，再交给产品 review 一遍。仍有待确认项就单独列出来，不要默默按猜测实现。

## 2. 规划 → RoadMap

**改动涉及 ≥2 个模块、仓库或服务的需求，必须先生成 RoadMap 并等用户确认再动手。** 单模块的小改动可以只列阶段性目标和完成标准，不必写完整 RoadMap。

RoadMap 固定三段：模块介绍、约束、阶段性 goal。格式和拆解原则见 [references/02-roadmap.md](references/02-roadmap.md)。

模块介绍里把模块名、目录路径、职责写到能直接定位文件的粒度，实现阶段就不用反复全仓库搜索，省时间也省 token。

## 3. 分阶段实现

按 RoadMap 的 goal 顺序实现。如果环境支持 goal 机制（如 Codex 的 `/goal`），用每个阶段性 goal 建一个目标；否则把每个 goal 当成一次独立任务来做。

**每完成一个 goal 就停下来**：给出改动文件、做了什么、怎么自测的，提示用户 review 并确认后再进入下一个 goal。不要一口气做完所有 goal 再汇报。

## 4. 双重 AI 审查

实现和 review 用不同的模型/agent：自己实现，另起一个模型或 subagent 来 review（double AI check）。reviewer 的产出是**问题清单**，最终由用户逐条决策。流程、审查维度和四象限分工见 [references/03-review.md](references/03-review.md)。

## 全局约束

实现阶段始终生效：

- 关键方法和核心流程写足够详细的中文注释，说明为什么这么做、边界在哪、异常怎么处理，不要只用注释复述代码。
- 主流程加足量日志：关键分支、入参出参、外部调用前后、异常兜底。宁可多打不可少打——线上排查时日志是唯一定位手段。日志带上单号 / 用户 ID / traceId 这类关键标识。
- 从整体设计出发拆解：先定整体方向和模块间契约，再落到具体实现。不要"先实现一个小需求、再实现另一个小需求"。
- 复用现有的工具类、日志封装、异常封装，不引入新风格，不改无关代码，不做 PRD 之外的顺手优化。
- 需求或方案变化时，同步更新需求文档和 RoadMap，保持三者一致。

## 交付物

一次完整的需求应该留下：需求文档、RoadMap（含流程图，如果画了）、代码、review 问题清单与逐条结论。这些是答辩和晋升时的材料。
