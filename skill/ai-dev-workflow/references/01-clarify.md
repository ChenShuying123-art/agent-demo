# 澄清与需求文档

## 提问策略

先通读 PRD 和相关代码，再提问。提问前自己先回答一遍"这段到底要改成什么样"，把答不上来、有两种解释、和现有代码冲突的地方记下来。

- 一次抛一批编号问题，按主题分组（业务流程 / 接口数据 / 边界异常 / 上下游 / 灰度运维），方便用户逐条回答。
- 只问真正影响实现的问题。PRD 里写清楚的、看代码就能确定的，不要问。
- 根据回答继续追问，多轮进行，直到没有新的阻塞性问题为止。不要为了凑数量重复问。
- 抛出问题就停下等回答。不要自问自答，也不要"边澄清边开始实现"。

## 覆盖维度

按需求实际情况挑选，不必全部问到：

- 业务规则与边界：空值、重复、临界值、并发、幂等、权限
- 数据：来源、口径、一致性、历史数据兼容
- 状态流转与交互：状态机、异常态、失败后停留在哪个状态
- 上下游接口：入参出参、错误码、超时重试、向后兼容、谁先上线
- 日志 / 监控 / 埋点：要看什么、告警阈值
- 灰度 / 开关 / 回滚：怎么放量、出问题怎么退
- 性能与容量：数据量级、QPS、耗时要求
- 排期与依赖：上下游交付时间、联调节奏

## 需求文档模板

写成给人和产品看的文档，不是实现笔记。

1. 背景与目标：要解决什么问题，成功标准是什么
2. 范围：做什么，明确不做什么
3. 业务流程 / 状态流转：主链路 + 分支 + 异常
4. 各模块改动点：模块、目录、改什么、为什么
5. 接口与数据：入参出参、数据结构、错误码、兼容策略
6. 边界与异常：逐条列出澄清结论
7. 日志 / 监控 / 埋点
8. 灰度 / 开关 / 回滚
9. 风险与待确认项

## 自检

- 通读一遍，能不能不看代码就说出会怎么改；有看不懂的地方说明还没澄清完，继续追问。
- 交产品 review，确认满足他心里的标准。
- 待确认项单独列出，不要藏在正文里。

## 流程图

如果环境里有流程图 / diagram skill，且这个需求有值得画的流程或状态流转，生成一张图。好处是评审时更直观，答辩也是可以留下来的产出。没有这类 skill 就跳过，不要为了画图硬凑。
