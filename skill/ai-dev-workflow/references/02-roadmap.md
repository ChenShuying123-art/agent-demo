# RoadMap

跨链路、多模块的改动在动手前必须产出 RoadMap 并等用户确认。这是 spec 思想：先有设计图，再照着图一步步执行。RoadMap 分三段。

## 一、模块介绍

用表格列出本次改动涉及的每个模块：

| 模块 | 目录 | 职责 | 本次改动 |
| --- | --- | --- | --- |
| xxx-service | path/to/xxx | 这个模块是做什么的 | 加什么、改什么 |
| xxx-web | path/to/xxx-web | ... | ... |

目录写到能直接定位文件的粒度。这张表是为了让实现阶段不用再全仓库搜索。

## 二、约束

写清楚这次实现必须遵守的规矩：

- 关键方法、核心流程要有足够详细的中文注释：为什么这么写、边界在哪、异常怎么处理。用户是要逐行 review 这些代码的。
- 主流程加足量日志：关键分支、入参出参、外部调用前后、异常兜底。宁可多打不可少打，线上出问题要能靠日志直接定位到是哪个逻辑错了。
- 日志带上单号 / 用户 ID / traceId 这类关键标识，让一次调用的日志能串成一条链路。
- 复用现有的工具类、日志封装、异常封装，不引入新风格。
- 不改无关代码，不做 PRD 之外的顺手优化。

## 三、阶段性 goal

先给整体设计：模块之间怎么协作、数据怎么流转、谁调用谁、上线顺序是什么。再从整体拆阶段性 goal——不要跳过整体设计直接拆零碎任务。

每个 goal 写清楚：

- 目标：这一步要达成什么
- 涉及文件：具体到文件路径
- 完成标准：怎么算做完了
- 自测方式：怎么验证（用例、调用方式、断言）
- 依赖：依赖哪个 goal，或哪一方先上线
- 完成后停下来等人工 review

拆解顺序参考：先打契约（接口定义、数据结构、表结构）→ 再主链路 → 再分支与异常 → 最后灰度、兼容、清理。

## 确认闸门

RoadMap 写完先给用户确认，确认通过再开始写代码。实现中方案有调整，回来更新 RoadMap。
